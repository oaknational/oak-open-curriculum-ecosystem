# The best of each Practice

The body below is identical in every estate that holds this node; the frontmatter is this
estate's binding. The definition it executes is
[PDR-142](../../practice-core/decision-records/PDR-142-the-best-of-each-practice.md).

Ratified with its definition on 2026-09-21. Where an estate already holds a ratified
delivery node for the exchange, that node stays and re-points its `serves` edge here.

## Outcome

Every estate's Practice holds the highest standards and best capabilities any of them holds,
with the bad removed, at a cost the seats can carry, and the shared package is cut from that
state. Observable between any two estates: a dry-run merge of the text they share changes no
file, conflicts nowhere, and leaves no file waiting; each standard that was judged has one
observation every estate passes; every offer has an answer, and each adopted capability has
been demonstrated where it was adopted; the removals judged have been carried out, those
resting on the owner's word on that word.

## User groups and value

- The owner: attention goes to the products, never to reconciling copies of the Practice or
  correcting a seat for following text that is false where it stands.
- The seats of each estate: doctrine that is true where it is read, and one answer to one
  question whichever estate they work in.
- An estate that was not in the room: a text it can use without having been here, and an
  invitation, since its seat now has a channel to the exchange.

## The bet

Full alignment first: the owner's word. This exchange defines excellent, and nothing in it is
delayed or avoided because a package comes later. After it, in the owner's order: the third
estate moves into the lineage's repository; an installable package is extracted, to which every
estate contributes and to which every estate adapts its local Practice; and whether that
repository is later split is reviewed then.

Within the alignment, the ORDER is the bet. Text travels by bytes where they carry the concept
(PDR-142) and is judged AS it travels, in the one full read each merged file already gets:
waiting has a measured, compounding price,
and so does spreading what does not pay. The section both seats wrote twice goes first. The
owner's rulings reach every estate, so the standards that waiting files name are raised now, in
the estate that lacks them, the expensive ones included: judge first, then build. Offers are
LISTED early, because they are half the owner's sentence and cost a sentence each, and ADOPTED
once the text under them is stable. Removal runs alongside adoption: what a merge read finds
bad is proposed at once, in every estate that carries it, and what rests on the owner's word
waits only for that word.

Deliberately not done: a register row for every changed path; a
node for a lane that ends within a session; any new ritual. Drift is read at the daily
coordination fold the estates already run: a dry run of the merge, three numbers in the fold's
state line (files a clean merge would change, conflict hunks, files waiting). A seat opens a
merge lane on judgement. This is a habit of this exchange, since it reads another estate's
checkout on one machine, never Core doctrine. A second habit of this exchange: a text of this
weight gets one cold reading from outside the seats' own model family where one is available,
and the reader is not told which line the seats doubt (one instance; falsifier: two such
readings that find nothing the inside checks had not).

Runs whatever happens to this text: every lane the owner has already approved, every security
floor, and every bug, among them any failing shared observation.

## Success looks like

The observable state under Outcome. Convergence of text is one observable of four, never the
headline. This node does not claim that the estates become byte-identical outside the Core and
the text they share. What would show the method failing: conflict hunks OR the waiting set
rising fold over fold while the seats work the rows. The owner ruled full alignment first, so a
method that is not converging goes to the owner with its numbers; the seats do not re-decide it.

list. Numbers live in state lines and pull requests, never here.

# Bind a reusable innovation composition and elevation profile

## Authority and pickup

Born sketch under the 10 October 2026 programme design. The owner commissioned
this design and documentary incorporation; implementation awaits this node's
ratification and the specific approvals its acceptance requires. Accepted direction
is [ADR-233](../../../docs/architecture/architectural-decisions/233-retained-framework-and-configurable-instances.md).
Read the [architecture](../../../docs/architecture/oce-architecture.md) and
[programme route](../../reports/repo-architecture/oce-rearchitecting/README.md)
for source scope and decision homes. No team measurement is commissioned.

## Goal

One complete framework profile supports creating, configuring, evaluating, operating and retiring a declared capability experience, with semantic and human authority preserved across elevation.

## User groups and value

Innovation builders receive repeatable construction and honest evidence without having to invent lifecycle machinery in apps; decision owners can distinguish possibilities from demonstrated outcomes.

## Mechanism

Use the retained Innovation Kit definition and architecture-definition plan. Select an in-repo reference experience combining two available capabilities. Define capability registry/compatibility, composition, host/provider bindings, declared active/omitted capabilities, authoring/workbench, fixtures/evaluation, accessibility/design, trust/state, deployment/recovery, evidence/correction and retirement contracts. Explicitly bind canonical Practice, reusable technology bindings, organisation/policy packs and instance content as distinct authorities. Decide experimental-to-supported plugin/skill/guidance promotion evidence, source-to-generated distribution/version provenance, update/retirement and receiving responsibility with the existing Practice/distribution owner; no Practice rewrite is implied. These decisions block promotion of the affected distribution, not unrelated capability work. New audiences/writes/learner data activate separate obligations; shared custody does not override domain authority.

## Acceptance criteria

- **AC1** — repo-safe — One versioned composition/elevation profile and independent scenario covers construction, compatible substitution, failed capability, diagnosis, evidence, recovery and retirement without bespoke external mechanisms.

- **AC2** — repo-safe — Source responsibility table routes existing design, agent/content, Practice/plugin, demo and experimental material to maintained OCE homes; gaps have a bounded contract or explicitly separate delivery home.

- **AC3** — repo-safe — Evidence distinguishes demonstration, software conformance, operational readiness and educational claims; elevation preserves unchanged semantic contracts and adds only explicitly activated obligations.

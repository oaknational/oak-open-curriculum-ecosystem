> **POLARITY: ANTI-PATTERN.** The failure shape is using a description as a
> check on the thing it describes. The cures are the mechanical moves below —
> never "describe more carefully", which is vigilance and does not hold under
> completion drive.

# A Description Is Not a Check

**An artefact's description is generated by the same process that generated
the artefact, so its errors correlate with the artefact's errors.** A
description therefore cannot serve as a check on the thing it describes — and
a description is exactly what the next agent acts on. The class is cross-agent
(two seats independently named it as their own error signature in one evening)
and it concentrates where confidence is highest: summaries of one's own work,
transmitted descriptions of discovered artefacts, and green outputs of
self-authored probes.

Every recorded instance was caught from OUTSIDE the generating context — `git
show` against a landing record, a type gate, a specialist reviewer, the owner —
and none by the author re-reading their own description.

## The faces

- **Committed description vs diff**: a commit message described a conserved
  copy as a refinement "carrying the mask-icon idiom"; the diff re-added the
  hotlink the cure had removed. The message was the opposite of the change.
- **Transmitted description vs source**: a discovered artefact summarised
  confidently without a first-hand read (an older copy called a refinement; a
  record carded for owner ratification unread — the owner's "did you evaluate?"
  forced the read that found what the summary missed).
- **Self-report vs behaviour**: a defect (theme script left loading with its
  control hidden) stated in a summary as a benefit.
- **Probe green vs probe validity**: a conflict probe piped into a marker grep
  reported 0 on a merge that then conflicted — the deprecated invocation's
  output shape was never verified, so its PASS was indistinguishable from
  mis-invocation. A later "fix" to a 16-cell test matrix silently ran every
  cell in one theme, and it went green.
- **Loop log vs remote state**: ceremony logs under- and over-reported
  reply/resolve outcomes while the remote held the truth, in both directions.

## Cures (structural, in the order they bind)

1. **Treat any claim ABOUT an artefact as unverified until read FROM the
   artefact.** Before acting on, committing over, or transmitting a
   description, read the described thing first-hand: `git show` the diff, open
   the live surface, read the record end to end. The read happens BEFORE the
   description crosses a boundary (a commit, a card, a handoff, a broadcast).
2. **Prove a guard or probe by breaking it first.** A checker's pass counts
   only after a negative control has shown it CAN fail — see
   [`prove-the-checker-with-a-negative-control`](prove-the-checker-with-a-negative-control.md).
   A test that establishes a precondition asserts that precondition.
3. **The verdict surface is the artefact/remote, never the narration.** Verify
   outcomes on the remote (GitHub state, the rendered page, the landed file),
   not in the loop log that narrated the attempt.
4. **Point external review at descriptions, deliberately.** Since the class is
   invisible from inside the generating context, route reviewer and successor
   scrutiny at summaries, commit messages, and handoff claims about artefacts —
   that is where this class lives, and sibling-surface sweeps catch what
   edit-path reads miss.

**Prediction (PDR-130)**: with this pattern live, handoff verifications and
review rounds that apply cure 1 (read FROM before acting on ABOUT) catch
description↔artefact divergences BEFORE they steer work — measured as
diverged-description catches logged against this pattern (already 16
instances within 48h of authoring, four caught by a verification pass that
applied the pattern to its own author's handoff). Falsifier: a quarter with
zero logged catches while handoffs continue — the pattern is decoration and
the cure needs a mechanical home (a handoff-verification gate) instead.

## The method

1. **The measure.** `dry_run_merge.py` lists every path under the six Practice-wide prefixes
   (`.agent/directives/`, `.agent/rules/`, `.agent/skills/`, `.agent/practice-core/`,
   `.agent/sub-agents/`, `.agent/hooks/`; `/evals/` and `/fixtures/` out) present in both tips
   and three-way merges each differing pair against the transplant pin: `dry-run-merge.md`
   beside this file carries its numbers at the read tips (445 shared, 279 identical, 166
   differing; 72 clean, 89 in conflict, 5 with no base; 46 and 59 waiting). `dump_hunks.py`
   writes every conflict hunk with its JC, BASE and OCE sides (`--diff3`) for the reading;
   `classify_conflicts.py` showed that host-token normalisation resolves one file of the 89, so
   the hunks are the ledger's read. The survey's new output, `inventory-v2.md`, the whole
   Practice at the tips its header names, sits beside them with its generator.
2. **The four readings** (plan Mechanism item 3), one per hunk and per one-sided file, each with
   its evidence (a quoted span from each side, at most fifteen words): `same meaning` (host name
   or wording that carries the concept; PDR-142's merged-text reading; the row names what the
   landing takes), `host binding` (a parameter the entity will carry, named, both values; §(f)),
   `capability gap` (joins the carry queue as one capability with the files in its closure and a
   size in pull requests; §(d)), `host-local` (the reason, under the membership tests of PDR-143
   §2; §(g)). The clean merges take three readings of their own: `lands merged`, `host-bound
   inside` (the merged text is true only with a parameter, a host tag or a standard raised in the
   receiver) and `contradiction` (a clean merge that doubles a block, rewrites an owner's verbatim
   word or a dated record). Governing texts: PDR-142 §Decision and §How we judge, PDR-143 §1 and
   §2, `best-of-each-practice` §Outcome, the plan's Mechanism item 3.
3. **The readers.** Six reads, session files outside the repository tree (this ledger is their
   durable home), carried here row for row: the directives, hooks and Practice Core hunks (19 files, 56 hunks); the rules
   hunks (34 files, 46 hunks); the skills hunks (14 files, 49 hunks); the reviewer templates and
   the sub-agents index (22 files, 56 hunks); the 72 clean merges; the 105 one-sided files.
   §(a) carries the four hunk reads with one column set, the file paths made absolute from the
   repository root; the readers' own carry numbers and row numbers are kept where their doubts
   cite them, with the mapping to the ledger's ids stated above each table.
4. **The placeholders.** JC.net's lineage-name gate keeps the organisation login and the
   repository name of the Practice's lineage off its surfaces, and this ledger is the same bytes
   in both repositories, so three strings the reads quoted are written as declared placeholders:
   `@<oce-org>` for OCE's npm organisation scope, `<the OCE repository's GitHub URL>` for the
   absolute links one skill carries, `<the OCE SonarCloud project key>` for the key one rule
   names. One more mechanical change: a quoted link fragment in a row has its `](` parted as `] (`,
   because both repositories' link validators read every markdown file, strip only single-backtick
   spans, and would read a quotation as a broken link; the closer parts a dump's first lines the
   same way before matching anchors. The one bare URL a quotation carries is wrapped in angle
   brackets for the markdown gate. Nothing else in the rows was changed.

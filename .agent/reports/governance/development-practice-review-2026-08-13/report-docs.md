## Docs and ADR review: `docs/governance/development-practice.md`

**Scope**: the 426-line worktree copy at `.claude/worktrees/identity-switchboard-pr2/docs/governance/development-practice.md`, which is `origin/main` plus one 60-line section (§Mutation testing, commit `3c7124be7`). ### Accuracy defects (verified against the repo)

**Stale freshness stamp.** Line 11 reads `**Last Updated**: 2026-07-04`, but the newest content in the file is the worked instance at line 114 dated 2026-08-13, added by the very commit that introduced §Mutation testing without touching the stamp. Separately, the stamp convention diverges from its neighbours: `README.md`, `DATA-SOURCES.md`, `safety-and-security.md`, and `sonar-disposition-policy.md` all use frontmatter `last_reviewed`; only this file and `logging-guidance.md` use a body-level `**Last Updated**`, which no validator reads.

**Three script names that do not exist.** Line 61 cites `format` and `markdownlint`; root `package.json` has `format:root`, `format-check:root`, `markdownlint:root`, and `markdownlint-check:root`, and no bare `format` or `markdownlint`. Line 72 cites `smoke` as a testing-layer command; there is no `smoke` script in root or in any workspace. What exists is fourteen individually-named `smoke:*` scripts in `agent-tools/package.json:21-34`. An agent reading layer 5 as a runnable gate list gets a command-not-found.

**The aggregate-command claim contradicts AGENT.md and ADR-121.** Lines 33-35 say aggregate commands "remain convenience workflows for local human development" and direct AI agents to one-gate-at-a-time runs instead. `.agent/directives/AGENT.md:246-247` says the opposite to the same audience: "Run gates one at a time while iterating; use `pnpm check` for canonical aggregate verification." ADR-121 §Local commands calls `pnpm check` "the canonical aggregate gate and the most comprehensive". An agent following this document would skip the canonical gate believing it was a human convenience.

**"Before each commit" does not describe the enforced surface.** Line 18 instructs that all seven listed gates run before every commit. `.husky/pre-commit` runs staged-file prettier, staged-file markdownlint, repo validators, and shell lint — it does not run `build`, `type-check`, or `test`. ADR-121 defines pre-commit as the fast (<60s) surface and pre-push as the thorough one. The instruction is stricter than the repo's own ratified surface model and gives no way to tell which is authoritative.

**The environment-configuration rule is unsatisfiable as written.** Lines 393-398 require `.env.local` files to mirror `.env.example`. There is no root `.env.example` — the root holds only `.env.local`. `docs/operations/troubleshooting.md:135-136` states this explicitly: "Write credentials to that workspace's `.env.local`; there is no root `.env.example`". The four real `.env.example` files are per-workspace. The rule is correct only under a workspace scoping that this document does not state and another document does.

Everything else I checked is true. `@oaknational/eslint-plugin-standards` is the real package name (`packages/core/oak-eslint/package.json:2`) and it does carry boundary rules, `max-files-per-dir`, and prohibited-import rules as line 63-67 claims. The root has no `scripts/` directory, so the ADR-168 §5a claim at lines 418-420 holds. `augmentBody` still exists at `packages/sdks/oak-curriculum-sdk/src/client/middleware/response-augmentation.ts:94`. Every Stryker claim checks out: `stryker.config.base.ts` at root, `packages/core/type-helpers` the only workspace with both a `mutate` script and its own `stryker.config.mjs`.

### Structure and consumers

**Who reads it and how they reach it.** `docs/governance/README.md:17` places this document first in the "5-minute reading path" for new contributors, described as "coding standards and workflow". `CONTRIBUTING.md`, `docs/README.md`, and `docs/architecture/README.md` all point at it. ### Recommendation, reasoned from the findings

**Structure is a real issue here, but the fitness number is not the reason.** Being in the `hard` zone is explicitly routine per ADR-144 §3, and seventeen files share that state. If the size signal were the only evidence, the correct response would be to note it and move on. The evidence that makes structure an issue is independent of the number: five unrelated doctrine axes in one file, three separate anchors from a single directive, two sub-agent templates reading it for two different concerns, and duplication of content that another document declares as its SSOT and has already recorded one silent-drift incident about.

**Fix the accuracy defects first, unconditionally.** The six defects above are true regardless of what happens to the file's structure, and two of them — the aggregate-command contradiction and the phantom `smoke`/`format`/`markdownlint` commands — actively misdirect the agents this document exists to direct. This work does not depend on any structural decision.

**The two highest-confidence structural moves are de-duplications, not splits.** Replace the command list (lines 18-31) with a pointer to `docs/engineering/build-system.md` §Quality Gate Commands and ADR-121's coverage matrix, and replace the markdownlint block (lines 338-359) with a pointer to `.agent/rules/markdown-code-blocks-must-have-language.md`. Both targets already hold the content in fuller form and both explicitly claim it. This is SSOT repair, not trimming — no substance is lost, so it does not engage the prohibition this document states at its own lines 376-377 ("NEVER compress docs to meet line limits") or PDR-067's preservation discipline. It also cures four of the six accuracy defects at the root, because the drift cannot recur once there is only one copy.

As a by-product, those two removals take roughly 35 lines out and land the file near 385 — clear of the critical boundary it currently sits on. That is a consequence of the fix, not its justification, and I would not present it as one.

**Then re-measure before deciding on a split.** If a split is still wanted after de-duplication, the cleanest seam is §Documentation Practice (lines 309-391, 83 lines) extracted to `docs/governance/documentation-practice.md`. It is the largest single-axis block, it has its own inbound anchor from `principles.md:162`, its audience (people authoring docs, ADRs, and plans) is distinct from the coding audience the governance README advertises, and the extraction is exactly what the file's own `split_strategy` frontmatter prescribes. The `typescript-practice.md` / `typescript-gotchas.md` pair is the existing precedent in the same directory.

**Do not split the gates cluster.** `principles.md` deliberately points here for the taxonomy and that reference is load-bearing and correct. Moving it would re-point the one anchor doing real architectural work, in exchange for nothing.

**Do not attempt a wholesale decomposition now.** 199 inbound references, most in archives, reports, and comms logs that archive discipline forbids retro-editing, mean a multi-way split multiplies the re-pointing surface and the risk of stale pointers — for benefit the two de-duplications largely already deliver.

**Raising the limits is available but is the wrong diagnosis.** ADR-144's post-mortem question 2 permits reconsidering `fitness_line_limit` when a file's role has legitimately grown, and ADR-144 §290 makes `fitness_char_limit` owner-only. But the evidence here is not a mis-set threshold; it is a file carrying five axes. Raising the ceiling would suppress the signal without touching the cause.

**Smaller items worth folding into whichever pass happens.** Move §Response Augmentation is Best-Effort (lines 275-279) to TSDoc on the middleware it describes or to the SDK's own docs. Add `build-system.md`, `principles.md`, `problem-hiding-patterns.md`, and `validation-strategy.md` to §Related Documentation (lines 422-426), which currently lists three entries and omits the document it duplicates. Add Stryker to `docs/engineering/tooling.md` so the tool inventory is complete. Give taxonomy layer 8 ("Specialist review") an inline pointer at line 77 rather than leaving its policy 65 lines downstream at line 142. And either convert the body stamp at line 11 to frontmatter `last_reviewed` to match the four other governance docs, or update it — right now it is both stale and unvalidatable.

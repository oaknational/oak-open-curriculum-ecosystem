7 · What the baseline says, in four sentences

1. The declared four-level hierarchy and the real structure diverge — the runtime spine is one small confirmed core sink plus domain clusters, with the declared libs/sdks seam bidirectional in production.

2. The real law is islands of hard enforcement in a sea of convention — six depcruise rules, a design fence, a membership whitelist — while whole change-clock families have no mechanical signature.

3. Lifecycle mixing is universal where generation exists: no generated-only package, four clocks inside one workspace at the worst site, 42.5% of tracked bytes generated-or-data.

4. The toolkit ambition is currently inverted: reusable machinery sits inside Oak leaves (OAuth-for-MCP, the OpenAPI pipeline, index lifecycle machinery), three built libraries have zero consumers, and nothing ships as a building block.

8 · Change proposals

The complete change set, each change a designed system property with its own diagram, per the brief's five points: the existing architecture holds no privilege; the thinnest possible Oak on reusable code; foundations designed to library grade and effectively finishable — constitutive of the conceptual shape, not a cleanup phase; one lifecycle per package; a toolkit that can build any digital service. The set was re-derived in full at the owner's lens-4 sweep (2026-08-19: "would this be simpler, or thinner, if we changed the system?" applied to every decision) — the shared generator that survived the sweep: convert standing activities (classifying, finishing, publishing, auditing) into constructed properties, and run the context-specificity gradient below the repo boundary (ecosystem-canonical → toolkit-owned → oak-pack).

Change 1 · The foundation layer, designed

Establish a chartered foundation tier: a small set of packages, each the canonical form of one standard concept, designed to be finished. This tier is the constitutional part of the toolkit — brief points 3 and 5 made structural — and its design is part of the repo's conceptual shape, not a cleanup phase. The estate's embedded instances serve as demand evidence and test cases; each package is designed from the concept's canonical form, never extracted from incumbent code (point 1 applied at code scale).

The charter. Admission asks question zero first (added at the owner's lens-4 sweep, 2026-08-19): does a finished canonical form already exist in the ecosystem? Where it does — an industry contract like OpenTelemetry's provider-neutral observability API, a mature result library — the default is ADOPT (with a thin conformance suite as the assurance bar), because the finish bar is precisely what those packages already paid, and re-deriving them in-estate privileges the incumbent shape one level deeper than point 1 tolerates. Owning is the evidenced exception: concepts with no external canonical form, or concepts small enough that owning a finished forty-line module genuinely beats curating a dependency — the crossover is depth-versus-curation-cost, and the estate's overrides block is the measured instrument for the curation side. Beyond question zero, admission requires a standard concept whose contract can be stated without Oak, any vendor, or any consumer class; at least one embedded estate instance as demand evidence (standard concepts do not wait for a second consumer); and a closed public API statable without present callers. The finish bar, declared at each package's birth: exhaustive tests (property-based where the concept warrants them), full documentation, a performance characterisation, and tier-closed dependencies — foundation depends only on foundation, preserving the one structural property the current core already proves. A finished package is done: its clock is designed flat, and later change is exceptional and deliberate. Finished is an observable, not a mood: ratified contract + green exhaustive suite + perf record + flat clock over a declared window + live consumers (§6 makes the clocks measurable; a flat clock alone can be abandonment).

The v1 concept set, with its demand evidence. Today's core is a mixed bag: genuine concept packages sit beside build infrastructure on a different clock, and two of the ten name a consumer class in their own descriptions — "for MCP applications" inside a tier that must not know its consumers.

Warrant. Evidence basis: the manifest and dependents sweeps plus the measured clocks above — no whole-estate enumeration was needed, so the design-first order holds for this change.

Falsifiers. A concept whose contract cannot be stated without Oak, vendor, or consumer specifics is relocated, not admitted. A concept with no embedded estate instance is deferred — demand unevidenced. If a finished package's clock will not go flat because consumers keep forcing contract change, the concept was mis-drawn: split or re-draw it rather than reopening the contract piecemeal. And on question zero, both directions: an adopted external that forces floor-management at a rate exceeding what owning would cost (the overrides-block class, measured) flips that concept to owned; an owned package whose ecosystem equivalent has become the industry contract flips to adopted — per concept, at its own card, never wholesale.

Spend. This change is design; the per-package finish work (contract, tests, docs, perf) is priced per package at its own card before any of it starts.

Change 2 · One clock per package

Brief point 4, made structural: a package's clock is the thing that changes it — authored design, upstream spec, regeneration, editorial curation, vendor churn — and no package holds two. Mixed clocks make every tick look like change to everything in the box: clocks become unmeasurable, review rounds oversize, and Change 1's "finished" observable is unreadable exactly where it matters. §4 shows the mixing is universal today — no generated-only package exists, and the worst site holds four clocks in one workspace.

The designed concept: the carrier contract, with a disposition rule. Every generated or derived artefact gets one of three homes, chosen by a rule rather than case-by-case taste — and the rule's default was inverted at the owner's lens-4 sweep (2026-08-19): untracked derivation is the default home; tracking must be earned. Untracked build product — the default: derivable at build time, built, never committed (the widget bundle, the orientation digest). Tracked carrier package — only where tracking earns itself through network dependence, expensive compute, or upstream instability, and consumers import the pinned result at source time: the package holds the regeneration command, its input pins (spec version, corpus snapshot, generator version), no authored logic, and a clean-regeneration check (regenerate → empty diff) as its gate — this is what keeps a cold clone building without touching the upstream, the Cardinal Rule's own property. Out-of-tree store — when it is a cache or input corpus (schema-cache, the 746 MB bulk downloads): named location, refresh contract, never in the tree. The carrier contract is itself a toolkit piece — it works for any generated surface in any digital service.

The measured 95% vocab-mining ↔ corpus-data co-change is engaged, not ignored: it is the expected generator-fan-out signature — when the generator changes, its output regenerates in the same commit — and the split makes it exemptable in the coupling measure instead of a smear across one box.

Warrant. Point 4 verbatim, plus two measured facts: the clocks are real and separable (§6 measures five distinct rates inside today's mixed boxes), and generation is 42.5% of tracked bytes — so this one change moves more of the estate's mass than any other. It also feeds Change 1 directly: one-clock packages are what make the stability gradient readable. Evidence basis: §4's byte census and §6's clock record, re-verified against the live tree 2026-08-19 — design-first holds.

Falsifiers. A carrier whose clean-regeneration check cannot be made deterministic names a generator-determinism defect — fix that first; the carrier design is not at fault and does not proceed around it. A carrier whose contents tick on two independent causes with different review needs splits again. If vocab-mining ↔ corpus-data co-change persists across the new seam after the fan-out exemption, the seam is drawn wrong — remeasure before proceeding.

Spend. Design only, here; the mechanical moves are cheap but the carrier gates (clean-regen checks) are new CI surface — priced at their own card with the first carrier as the proving instance.

Change 3 · Thin Oak on reusable ground — the seam

Brief point 2, answered at the system level. An earlier draft of this change executed the census's per-package dispositions inside the current tree; the owner's lens-4 question (2026-08-19, "would this be simpler, or thinner, if we changed the system?") superseded it: per-package splits treat leakage one package at a time and leave the leak vector open, with classification as a standing activity. The system change makes thinness a construction property instead of a policed one.

The change: two sides, one seam, three gates. The code estate re-homes under two top-level families — toolkit/ (generic by construction, publishable by default) and oak/ (packs and assemblies) — with the seam enforced by three mechanical gates: imports (toolkit/** never imports oak/** — dependency-cruiser), lexemes (no Oak vocabulary — brand names, curriculum terms, thenational.academy — inside toolkit/ sources; the @oaknational npm scope stays, as provenance rather than coupling), and manifests (toolkit packages carry publishable manifests by default). The probe "could a non-Oak service consume this unchanged?" stops being a review question and becomes a construction fact; a machinery package cannot acquire Oak-ness without failing a gate at write time. And Oak-ness becomes enumerable: oak/ can be pointed at and measured, so "thinner" becomes a number with a trend, not an aspiration.

Oak-ness inside oak/, by class. The three pack classes survive as the oak side's internal structure — identity packs (brand, reserved), content adapters and data packs (OGL), injected configuration (names, policy, env) — plus the assemblies (apps and demos). The licence model lands directory-literal: toolkit/ is MIT, the oak side carries the OGL content pointers and the reserved brand, and no component's licence needs more than one word again. The design system remains the proven instance of the pattern — same markup, any identity — now generalised by topology rather than by per-package discipline.

The census retires into a migration map. The classification matrix (45 subjects, owner-carded 2026-08-14) stops being a standing instrument and becomes the one-time re-home plan: the 12 generic-foundation rows move to toolkit/ nearly as-is; the 9 mixed rows split once at the seam, each along its already-named line; the 17 oak-leaf rows re-home under oak/. §7's inverted-ambition instances — OAuth-for-MCP, the OpenAPI pipeline, the index lifecycle machinery — exit Oak leaves as toolkit machinery in the same move. After the migration, membership is the classification, and no census of this kind needs running again.

Warrant. The owner's lens-4 ruling plus three owner principles landing on the same answer: structure over vigilance (a needs-vigilance boundary is unfinished), correctness by construction, and licence legibility. The census evidence supports feasibility — every mixed row already carries a named single split. The one-time re-home is mechanical (import paths, workspace globs, CI wiring) and buys the ongoing classification cost down to zero. The maximal form — a separate published toolkit repo — was considered and deferred: it maximises the seam but pays in change-cost, the owner's core currency; its flip condition is external toolkit adoption with third-party contributors becoming a product goal.

Falsifiers. A substantial class of true hybrids — mixed rows that resist even one split without forking machinery — means the seam is drawn wrong for this estate: stop and remeasure. If the lexeme gate cannot run mechanically without false-positive noise drowning its signal, that leg weakens to review-time and the seam loses one of its three teeth — name it rather than pretending. An Oak element that resists pack or configuration form marks either machinery not yet generic (fix the machinery) or genuinely Oak-constitutive behaviour (it lives in oak/, named as such).

Spend. Design here; the re-home is one migration card (mechanical, Cardinal-Rule machinery already proves the estate can re-align wholesale), and the three gates are new CI surface priced with it. The per-row splits of the earlier draft become steps inside that one card instead of twenty-six separate ones.

Change 4 · The delivery plane — absorbed into the seam

Resolved at the owner's lens-4 sweep (2026-08-19): once Change 3's manifest gate makes the toolkit side publishable by default, "start publishing" stops being a programme and becomes a property — this change's substance lives in the seam, and its diagram is Change 3's. One genuine decision remains as residue and rides the seam's migration card: the release mechanism itself — per-package versioning and publishing against today's single-version pipeline that tags and changelogs but never publishes (npmPublish: false). Publishing stays the exercised proof of separability; the seam is what makes the proof cheap.

Change 5 · The workspace-liveness gate

Reshaped at the same sweep from three ad-hoc dispositions into a system change: an estate-level check under which a workspace with zero consumers and no deployment target fails unless it carries a dated warrant. Package-level dead-code tooling (knip) cannot see this class — a whole package with no importers is invisible to per-package analysis, which is exactly how three built libraries accumulated silently. The gate composes with Change 1's stability observable (live consumers is one of its legs) and closes the class permanently; the estate's follow-up discipline supplies the warrant shape — every warrant carries its own expiry and its named gate. The first run IS the disposition moment for today's three instances — graph-ingest, graph-project, oak-design-ink: finish, adopt, or retire, each with its evidence, at one card.

Warrant. The class exists by measurement (three instances in §1's family grid) and per-package tooling structurally cannot catch it. The gate converts a recurring audit into a constructed property — the same generator as every change above.

Falsifiers. If legitimate incubation (a package built ahead of its consumer by design) keeps tripping the gate, the warrant mechanism is too coarse — tune the warrant shape, never the gate's teeth. If the first run cannot reach a disposition for any of the three with evidence in hand, the finish/adopt/retire triad is missing an option — name it.

Spend. The gate is one validator plus a schema for warrants; the first-run dispositions are one card.

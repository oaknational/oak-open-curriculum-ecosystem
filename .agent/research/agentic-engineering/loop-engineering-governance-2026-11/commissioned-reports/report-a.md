## 4. Answers 1 to 23

### Loop engineering

**1. W1's definition and building blocks.**
W1 opens by defining loop engineering as replacing yourself as the person who prompts the agent and designing the system that does so. It calls a loop a recursive goal: you define a purpose and the AI iterates until complete. It places the practice relative to its earlier harness post: "Loop engineering sits one floor above the harness." (W1)

The list, under the heading "The five pieces, and then notes", in order: (1) automations, which fire on a schedule and do discovery and triage unattended; (2) worktrees, so parallel agents do not collide; (3) skills, which write down project knowledge the agent would otherwise guess; (4) plugins and connectors, which attach the agent to tools already in use; (5) sub-agents, so one has the idea and another checks it. Then a sixth item, memory: a Markdown file, Linear board or anything else outside the single conversation that records what is done and what is next.

*State:* yes. The prose calls the sixth item "memory"; the comparison table beneath has a sixth row labelled "State", with the job of tracking what is done. The table's column header for all six rows is "Primitive".
*"Gate":* I did not find the word in the page text. W1 speaks of a verifier, a checker and a stop condition instead.

**2. W5's six primitives.**
Not found in this source: W5 is paid and the preview stops before the body. The preview's own contents list names: where loops came from; the full anatomy of a loop; a 14-step roadmap from manual prompter to loop engineer; a catalogue of 41 pre-built loops; designing loops with Claude Fable 5; and where loops fail, what they cost and three debts. The phrase "six primitives" does not appear in W5's preview; it comes from Source A's description of W5. The preview's subtitle mentions a three-line bash script but does not name Ralph Wiggum. The 14 steps and the orchestrator material are behind the paywall. The preview reproduces Steinberger's post, dated there to 7 June 2026: "You should be designing loops that prompt your agents." (Steinberger, as reproduced in W5)

**3. W6 on Ralph.**
"In its purest form, Ralph is a Bash loop." (W6) The page shows a one-line infinite `while` loop that pipes a prompt file into a coding agent. Huntley describes it as a technique, monolithic by design: one process, one repository, one task per loop, with the plan file and specifications loaded into context identically on every iteration and expensive work pushed to sub-agents.

- *Stopping:* no stop condition is given. The loop as shown never exits. The page says the TODO list eventually empties or the agent goes off track, at which point the operator judges, often by discarding the list and regenerating it, or by a hard git reset. It says to expect to wake to a broken codebase from time to time.
- *Cost:* one relayed anecdote of a contract valued at $50k delivered for $297 in spend. The page concedes the method is wasteful because the specifications are re-read every loop, and says the tool must not cap tool calls or usage.
- *Safety:* not found in this source in the sense of sandboxing, permissions or budgets. What it does say: back pressure (types, tests, static analysers, scanners) rejects bad output; only one sub-agent should run build and test; senior engineers are still required; and the author would not use the technique on an existing codebase, only for greenfield work he expects to get about 90% done.

**4. W11's loop types.**
"loops as agents repeating cycles of work until a stop condition is met" (W11). The types are classified by trigger, stop, primitive and suitable task. From the closing summary table:

| Loop | What you hand off | Primitive |
| --- | --- | --- |
| Turn-based | the check | custom verification skills |
| Goal-based | the stop condition | `/goal` |
| Time-based | the trigger | `/loop`, `/schedule` |
| Proactive | the prompt | all of the above plus dynamic workflows |

*Stop conditions:* turn-based stops when the model judges it is done or needs context; goal-based stops when the goal is met or a turn limit is hit, with a separate evaluator model checking the condition each time the agent tries to stop; time-based stops when cancelled or the work completes; proactive tasks each exit on their goal while the routine runs until switched off.
*Budgets:* expressed as turn caps written into the goal (the example stops after five tries), interval length, model choice, piloting before large runs, scripts for deterministic work, and usage-review commands. The page notes that dynamic workflows can spawn hundreds of agents and that an agent can be stopped at any time from the workflows view. No monetary budget control is described.

**5. W12.**
Abstract page only; the abstract is paraphrased, not reproduced. The paper is an exploratory review of grey literature on loop engineering, a research agenda derived from it, an analysis of which aspects can be traced in repository data, and an exploratory mining study. The review finds broad agreement that a well-engineered loop has: triggered agent runs bounded by machine-checkable stop conditions, persistent state files, verifier sub-agents, token budgets, and defined points of escalation to humans. The mining study covered 36,710 repositories; heuristics matched 256; autonomous agent loops were confirmed operating in 217 of those. Finding: repositories commit the configuration around loops, but "almost none commits the state files the discourse prescribes" (W12), and runtime state stays outside version control. A controlled study of autonomy levels is planned, not reported. The abstract notes bold claims and vocal scepticism around the term without naming anyone.

### Harness

**7. Definitions of "harness".**
- *W4:* the harness is every piece of code, configuration and execution logic that is not the model. "A raw model is not an agent." (W4) Parts listed: system prompts and instruction files (CLAUDE.md, AGENTS.md, skill files, sub-agent prompts); tools, skills, MCP servers and their descriptions; bundled infrastructure (filesystem, sandbox, browser); orchestration logic; hooks and middleware for deterministic execution; observability including cost and latency metering. *Coinage:* W4 says Viv Trivedy coined "harness engineering".
- *W3:* the harness is the walls around a loop: its sandbox, the tools it can reach, memory that survives between runs, and the gates that decide what "done" means. The loop is the behaviour; the harness is the environment. No credit for the term.
- *W2:* in passing, an agent is a model plus a harness of files, tools, memory, skills, sandboxes, permissions, observability and recovery.
- *W13:* "An agent is a model plus a harness" (W13): the runtime coupling an LLM to the world. Seven subsystems (section 2.3, Table 1): agent loop; LLM integration; tools and actions; memory and context; safety and permissions; orchestration; extensibility. Two cross-cutting surfaces sit beside them: the interface layer and the session substrate. *Coinage (section 2.1):* the term entered circulation in February 2026, first used in passing by Mitchell Hashimoto, then defined and elaborated by Trivedy in LangChain's Deep Agents work. W13 adopts Macedo's definitional core and extends it.

### Inner loop and outer loop

**11. W2.**
"Engineers own the outer loop." (W2) The inner loop is where the work is done: investigate, implement, verify, report. W2 calls this capability and assigns it to agents. The outer loop is agency: decide, verify, approve, own. The boundary between them is evidence, which crosses to a human who owns the dependent system. Three terms frame the talk: Quality (checks installed beforehand), Verdict (the ship decision) and Answerability (being able to explain why).

The four loops where W2 wants the human, in order: the constraints loop (which inputs, architectures, instructions or invariants to set); the sampling loop (how much output to sample and review); the audit loop (what evidence to keep and whether the audit log works); the ownership loop (which part of the production boundary to own).

Evidence cited: Sonar's 2026 State of Code report (42% of committed code AI-generated or significantly AI-assisted); GitLab's June 2026 AI accountability research (review and validation are bottlenecks; governance usually follows code creation); OpenAI's work on agents and work (hour-scale delegation); a Wharton study (nearly three-quarters accepted a wrong AI answer); an Anthropic randomised controlled trial (50% against 67% on a comprehension quiz). Three hidden costs are named: cognitive surrender, cognitive debt, orchestration tax.

**12. W9.**
- *Open:* nothing the result reveals reaches the agent again. Repetition alone is not feedback.
- *Closed:* a check measures the result and a failure goes back to the agent with what the check found. W9 keeps this control-theory sense and rejects "closed" meaning "runs without people"; for that it says to use "unattended".
- *Inner:* the fastest loop around one piece of work; seconds to minutes.
- *Outer:* contains inner loops and crosses a boundary such as a review, schedule, pull request or production; hours or days.
- The terms are relative; the innermost loop is the agent's own tool loop, which the workflow cannot see into.
- *Gate versus loop:* a gate can only stop bad work; a loop sends it back.

W9 does not cite W2. The disagreement is definitional: W9's summary says inner and outer describe nesting, not who is involved, whereas W2 defines the pair by who does each. In practice W9 lands on a command closing the inner loop and a person closing the outer one.

**13. W10's three loops.**
- *Agentic coding loop:* given a specification and optionally evals, the agent writes code, tests it and iterates. Runs every few minutes.
- *Developer feedback loop:* a developer examines the product and steers the agent. Tens of minutes to hours.
- *External feedback loop:* friends, alpha testers, production A/B tests. Rarely less than hours, sometimes days or weeks. This feeds the developer's vision, which drives the specification, which drives the agent.

The image caption gives minutes, hours, days. Ng prefers to describe the human contribution as "humans having a context advantage" (W10) rather than taste, and says the developer step cannot be automated while the human knows something the AI does not.

### Light factory and dark factory

**14. Shapiro's levels.**
Shapiro's page gives the numbers and descriptions in running text; the level names appear in Willison's note (and possibly in Shapiro's images, which I could not read). Descriptions paraphrased from W7a; names from W7b.

| Level | Name (W7b) | Description (W7a, paraphrased) |
| --- | --- | --- |
| 0 | Spicy autocomplete | Nothing reaches disk without your approval; AI is a search aid or an occasional accepted suggestion. |
| 1 | Coding intern | You write the important parts and hand off discrete tasks such as a unit test or docstring. |
| 2 | Junior developer | Pairing with the AI as a colleague in an AI-native tool. Shapiro puts 90% of "AI-native" developers here and warns this level feels finished but is not. |
| 3 | Developer | You are the human in the loop, reviewing diffs all day while agents run in several tabs. Almost everyone tops out here. |
| 4 | Engineering team | You write and argue over specs, craft skills, review plans, leave for 12 hours and check whether tests pass. Shapiro places himself here. |
| 5 | Dark software factory | "It's a black box that turns specs into software." (W7a) He knows a handful of teams of fewer than five people doing it. |

Shapiro models the scale on the NHTSA driving-automation levels. "Five levels" is zero-indexed, so there are six.

**15. W3.**
- *Loop:* one agent doing one job on repeat until a condition is met.
- *Software factory:* many harnessed loops running at once, fed by a queue and drained through a review gate into production, with humans owning it from above; an org chart made of loops, not a bigger agent.
- *Dark factory:* code ships that no human has read, verified only by machines. The image is borrowed from lights-out manufacturing.
- *Lit factory* (the body's word; the title says "Light"): the same pipeline with lights left on where judgement lives; a human reads output before it ships, and judgement moves upstream to product, design and architecture.
- *Back pressure:* a loop gets only as much autonomy as can be cheaply and reliably verified.

The rule, section "What earns a loop the dark": "A loop can earn itself fully automated status only if the check is cheap" (W3), and the sentence continues with two more conditions: the check runs at high frequency and rests on something not easily faked. Examples given: green-or-red oracles, type gates, property tests, a review agent with a real rubric. The oracle must answer immediately and not drift. Short loops qualify more easily; W3 relays Horthy's rule of thumb that an agent holds for three to ten steps and loses the thread past twenty. The converse: keep review where a wrong answer is expensive and only a person can catch it (subtle production bugs, large blast radius, decisions shaping a year of work; auth, billing and public API contracts are named). The stated danger is setting every switch the same way.

**16. StrongDM (W8).**
- *Rules (W8a):* code must not be written by humans; "Code must not be reviewed by humans" (W8a); plus a practical test of at least $1,000 of tokens per human engineer per day.
- *Verification without reading code:* "scenarios", meaning end-to-end user stories often stored outside the codebase like a holdout set and validated by an LLM; "satisfaction", the fraction of observed trajectories through the scenarios that likely satisfy the user; and a "Digital Twin Universe" of behavioural clones of Okta, Jira, Slack, Google Docs, Drive and Sheets, against which thousands of scenarios per hour can run. The page gives two reasons tests were not enough: too rigid, and open to reward hacking.
- *Spend:* the $1,000-a-day figure above. No total is given.
- *People:* three (Justin McCarthy, Jay Taylor, Navan Chauhan), founded 14 July 2025.
- *Willison's criticisms (W8b):* he asks how never reviewing code could be sensible given the mistakes LLMs make, and notes security software is the last thing one would expect to be built this way. His main objection is cost: at roughly $20,000 a month per engineer he finds the patterns far less interesting, a business-model question. He adds that sustainable software businesses look different when competitors can clone features in hours. He was otherwise impressed by the demo he saw in October 2025.

**17. Horthy (W15).**
- *Dates:* Horthy says that in November and December his team discarded its open-source product and rebuilt from scratch, calling this the end of his "don't read the code" cycle. The year is not stated; the episode was published in August 2026.
- *Duration:* not stated in W15. W3 gives about four months with no human reading the code and says trouble sets in three to six months into a project. A podcast summary says four months *(snippet, not opened)*.
- *What failed:* it became easier to rebuild than to repair. He describes code where fixing one place breaks another, and says models have no intuition for maintainability because it could not be taught in reinforcement learning. Given five features a day for six weeks, "you will wake up to a ball of spaghetti" (W15).
- *What he does now:* human alignment before code is written, in stages: product requirements with HTML mock-ups and a business metric; system architecture; "program design"; an outline; then code. Effort is aimed where expected pain (likelihood of error times cost) is highest. He recommends neither ceasing to read code nor burying senior engineers in pull requests. W3 adds an unattended loop he does run: a nightly job that fixes exactly one anti-pattern and opens one small pull request.
- *Written account by Horthy:* not found. W3 refers to "a recent post" without a link and links his 12-factor-agents repository.

### Swarms and the refutation gate

**18. "Refutation gate".**
Among opened sources the phrase appears only in Source A's preview. It is not in W1 to W4, W6 to W11, the abstracts of W12 to W14, the read portion of W13, W15 or W17. A web search for the exact phrase with "agents swarm" returned no page using it. Nearest wording found: W14's "promotion gate" at which adversarial agents try to disprove candidates; and a June 2026 third-party playbook describing a Kimi K2.6 swarm with a second model at a "verify gate" set to refute *(snippets, not opened)*.

**19. W14.**
Abstract page only. It proposes Refute-or-Promote, an inference-time reliability pattern for LLM-assisted defect discovery, not for coding-agent swarms. Components: Stratified Context Hunting for candidate generation, adversarial kill mandates, context asymmetry, and a Cross-Model Critic.
- *How the gate decides:* at each promotion gate adversarial agents try to disprove the candidate; cold-start reviewers are meant to reduce anchoring; cross-family review is meant to catch correlated blind spots. A candidate that survives is promoted. A mandatory empirical gate was added after the failure below.
- *Results:* over a 31-day campaign across 7 targets, about 79% of 171 candidates were killed before disclosure (retrospective); 83% on a 30-candidate prospective subset. Outcomes include 4 CVEs, judged by external acceptance.
- *Failure reported:* ten dedicated reviewers unanimously endorsed a Bleichenbacher padding oracle in OpenSSL's CMS module that did not exist; it was "killed only by a single empirical test" (W14). The abstract also says no vulnerability was discovered autonomously.

**20. Moonshot (W17).**
- *Swarm size:* W17b: "Deploy up to 100 sub-agents working in parallel" (W17b), with over 1,500 tool calls and results 4.5 times faster than sequential execution. These figures are for Kimi K2.5. W17a gives no number. A figure of 300 sub-agents for K2.6 appears on a third-party page *(snippet, not opened)*; Source A says "hundreds".
- *How it works:* a main agent decomposes the goal, creates and assigns sub-agents, receives findings and redistributes them; sub-agents can be re-engaged with prior context; the user can redirect mid-run. W17b calls it self-organising and an early research preview, with direct sub-agent communication and dynamic control of parallel width still to come. In Kimi Code it is started with `/swarm`. Swarm tasks use several times the credits of a single agent.
- *How swarm behaviour is trained:* not found in this source.
- *Whether Kimi K3 supports it:* not found in this source. Neither page names K3 in its body; the site navigation links K3 and K3.1 Pro posts, which I did not open.
- *vLLM minimum hardware:* not opened.

# Account to saved content

## Outcome and scope

A teacher or educator can identify themselves, complete the minimum account setup, save a curriculum unit, see that action reflected immediately, return to it in My Library and remove it later.

This trace covers the current static path from a unit save control through registration, onboarding, the OWA backend-for-frontend and the Educator API. It does not establish conversion, reliability, latency or whether the current onboarding fields are all product requirements.

## Observable contract

From the user's perspective, the journey should provide:

1. an explanation when saving requires an account;
2. a safe return to the point at which sign-in or onboarding began;
3. no pupil-account implication: the sign-in surface says pupil learning does not require signup;
4. immediate, accessible feedback when a save or unsave starts;
5. rollback and error feedback when persistence fails;
6. saved units grouped into useful curriculum collections on later visits;
7. isolation of one user's saved content from every other user.

Items 1, 3, 4, 5 and 6 are **Observed** in source. Items 2 and 7 are **Observed** as encoded intent, but need runtime and authorization tests before they can be treated as verified behavior.

## Identity and consistency model

**Observed:** Clerk is the identity and onboarding authority exposed to browser code. The Educator API is the durable store for saved content. OWA translates between them through user-specific BFF routes and a Clerk-issued Hasura token.

**Observed:** Educator-user provisioning has two recovery paths. A verified Clerk `user.updated` webhook attempts to create the Educator API user, while the save endpoint also creates one when absent ([webhook](https://github.com/oaknational/Oak-Web-Application/blob/510ac63a62fb37a70183b00ce0f5fb15be4491e5/src/app/api/webhooks/route.ts#L68-L87), [save fallback](https://github.com/oaknational/Oak-Web-Application/blob/510ac63a62fb37a70183b00ce0f5fb15be4491e5/src/pages/api/educator/saveUnit/%5BprogrammeSlug%5D/%5BunitSlug%5D.ts#L36-L52)). This makes user creation eventually recoverable, but the required idempotency belongs to the Educator API contract and is not established by this trace.

**Observed:** Saved state exists simultaneously as Educator API data, SWR data, hook-local arrays and a shell-level count. The save and My Library hooks each implement their own optimistic save/unsave sequence.

**Inferred:** The real application boundary is not "authentication" alone. It is an account capability spanning identity, onboarding eligibility, region authorization, durable user state, return navigation, optimistic consistency, analytics and failure recovery.

## Observed strengths and preservation questions

These mechanisms are visible in source. Their impact and necessity remain preservation hypotheses until product, user, operational or impact evidence establishes them.

- **Observed:** the product makes the account boundary explicit before an action and preserves account-free pupil access.
- **Observed:** safe redirect handling is used at both onboarding entry and exit.
- **Observed:** server endpoints derive user identity from the authenticated request rather than accepting a browser-provided user ID.
- **Observed:** provider responses are runtime-validated before My Library renders them.
- **Observed:** save and unsave provide immediate feedback and compensate after resolved non-OK responses; rejected-network compensation remains under [V003](../../investigations/validation-register.md).
- **Observed:** My Library presents saved units in curriculum context rather than as an unstructured bookmark list.
- **Observed:** webhook provisioning has an action-time fallback, reducing dependence on perfect event delivery.

## Seams and unresolved risks

1. **Third-party UI seam:** OWA uses Clerk CSS selectors, a mutation observer and polling to infer whether Clerk's form exists. A Clerk markup change can alter surrounding legal and pupil guidance without a type or API failure.
2. **Router seam:** Registration/onboarding use App Router, while My Library and educator endpoints use Pages Router. Return paths and metadata cross both shell profiles.
3. **Authorization seam:** Browser gates improve experience but do not authorize data. The BFF and Educator API token/row policies carry the security contract; this static review has not tested them.
4. **Consistency seam:** Two hooks duplicate optimistic mutation logic, and the shell count is updated independently. Cross-tab behavior, retry semantics and reconciliation after success are unknown.
5. **Provisioning seam:** Webhook creation and lazy creation are deliberately redundant or historically accumulated; ownership, idempotency and failure visibility need confirmation.
6. **Data-shaping seam:** The BFF joins saved identifiers to a curriculum browse materialized view, then the browser performs further presentation shaping. Behavior for retired, missing or partially published content is unknown.
7. **Side-effect seam:** Onboarding treats the Clerk update as critical, but local download migration, HubSpot submission and analytics follow with different failure handling. The user-visible completion guarantee across these effects is not explicit.

## Effect on hypotheses

- **H001, capability-owned modules:** supported for testing. The account outcome has a coherent cross-route contract, but its code is distributed across generic HOCs, UI, hooks, route handlers and provider clients. It would be weakened if the shared gates and mutation logic are demonstrably reused without capability-specific policy.
- **H003, unified runtime-shell contract:** narrowed. Account behavior crosses both routers, so parity matters at redirect, identity, notification and analytics boundaries; it does not imply one identical provider tree.
- **H004, domain ports and explicit freshness:** supported for testing. Saved-content reads and writes already pass through an OWA BFF, but consistency, stale behavior and missing curriculum content are not stated as a use-case contract.
- **H005, journey-level confidence:** supported for a discriminating experiment. Unit tests exist at individual layers, while the user outcome depends on Clerk redirects, metadata refresh, webhook/lazy provisioning, optimistic rollback and provider authorization acting together; the trace does not establish unique journey-test signal.

No hypothesis is promoted by this static trace alone.

## Next discriminating evidence

1. Run the journey signed out, signed in but not onboarded, and fully onboarded, preserving a path and focus target each time.
2. Inject Clerk UI changes or replace form-detection with an explicit provider state to test the fragility claim.
3. Exercise save/unsave with delayed, failed and duplicate requests, plus two tabs, and record reconciliation behavior.
4. Verify Hasura authorization with two users and attempted identifier substitution.
5. Simulate missing webhook delivery and repeated user creation to establish the provisioning contract.
6. Return retired, missing and mixed-publication units from the saved-content query and define the intended user outcome.
7. Map existing tests against the seven observable-contract statements above.

# Runtime-shell parity

## Question

Do the Pages Router and App Router implement the same application-level behavioral contract, and which differences are intentional?

This is a static comparison at the revisions in the [research charter](../research-charter.md). It cannot measure delivered client code, hydration work or establish product intent.

## Provider profiles visible in source

The static source suggests at least three shell profiles rather than one unconditional tree:

1. **Public and Pages profile:** broad client support for editorial, teacher and pupil routes.
2. **Core App profile:** server-rendered site chrome with the common root providers.
3. **Classroom profile:** common App root plus Classroom query context and journey analytics.

**Inferred:** H003 should be tested as a common contract with explicit profiles, not as one shared React component. A provider is part of the contract only when its user-visible or operational behavior is named.

## Observed strengths and preservation questions

These mechanisms are visible in source. Their impact and necessity remain preservation hypotheses until product, user, legal or operational evidence establishes them.

- **Observed:** consent controls analytics, feedback and error-reporting initialization.
- **Observed:** global reduced-motion rules and runtime accessibility diagnostics are applied across journeys.
- **Observed:** fonts and styled-components have server-rendering mechanisms intended to avoid unstyled content.
- **Observed:** application errors are reported and converted into full-page or nested fallbacks.
- **Observed:** navigation, notifications and preview behavior are composed outside individual feature views.
- **Observed:** Classroom adds entry-surface context without reimplementing the full root.

## Differences requiring intent or runtime evidence

| Difference                                              | Evidence needed                                              | Possible invalidator for H003                                                                                     |
| ------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `en-GB` versus `en`                                     | Accessibility/SEO requirement and rendered production HTML   | Difference is harmless and intentionally route-specific.                                                          |
| Legacy theme absent in App Router                       | Inventory of migrated components and visual/runtime failures | App routes have fully removed the legacy contract.                                                                |
| Overlay, toast and pupil providers absent in App Router | Consumer graph and route migration plan                      | They are Pages-only capability dependencies, not shell behavior.                                                  |
| Different Clerk options                                 | Product requirement and screenshots for equivalent flows     | Registration intentionally owns a distinct profile.                                                               |
| Analytics initialization paths                          | Network/runtime trace under each consent state               | Both mechanisms are behaviorally equivalent and migration-safe.                                                   |
| Sprite mounting                                         | Asset usage and failed-request/render checks                 | App routes have no sprite contract.                                                                               |
| SEO mechanisms                                          | Rendered head comparison for equivalent route types          | Exact parity is unnecessary because route outcomes differ.                                                        |
| Error boundary hierarchy                                | Injected-failure tests at component, layout and root levels  | Router semantics require distinct implementations but meet one outcome contract.                                  |
| Provider client workload                                | Bundle and hydration measurements for each profile           | A common implementation adds client work that violates an evidence-backed performance or interaction requirement. |

## Effect on H003

**Result:** The static comparison supports investigating H003 but does not yet support adopting it. There is clear overlap and meaningful divergence, but source alone cannot distinguish intentional profiles from migration drift.

The next discriminating work is a rendered parity suite for consent states, identity, page metadata, injected failures and representative UI dependencies, accompanied by bundle and hydration measurements.

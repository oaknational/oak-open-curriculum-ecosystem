# Curriculum authority and discovery projections

## Decision boundary

This record asks where curriculum facts, identities, relationships, discovery relevance and publication state are authoritative. It explicitly tests, but does not assume, that browse, exact retrieval, search and graph can be derived from one curriculum authority.

An API schema, generated SDK, index or graph is a representation. It becomes an authority only when evidence shows that it owns an enduring fact or decision rather than transporting, reshaping or accelerating another source.

## Current observation

- **Literal behaviour:** OWA resolves curriculum through a generated API client and application queries, creates route/browse models and combines curriculum with other sources. OCE contains a generated curriculum SDK, search capabilities and graph capabilities with their own packages, applications and architectural decisions.
- **Inputs and outputs:** published curriculum content and metadata feed API responses and generated types; applications shape them for routes and browse; search ingestion creates retrieval documents; graph work exposes identities and relationships for traversal and agent use.
- **State and authority:** upstream curriculum publication appears authoritative for many content facts, while search relevance, graph assertions, aliases, index versions and application routing may introduce additional state or interpretation. Exact ownership is not yet mapped field by field.
- **Dependencies and lifecycle:** OpenAPI generation, upstream availability, cached schemas, application builds/caches, search ingestion/index swaps, graph generation/storage and content publication/withdrawal have potentially different clocks.
- **Excellence currently delivered:** typed curriculum access, structured programme/unit/lesson navigation, multiple discovery paths, semantic and lexical retrieval work, ontology/graph context, fixtures and validation disciplines.
- **Difficult states and exceptions:** curriculum variants, canonical identity, renamed or withdrawn content, multiple programme contexts for one lesson, missing source data, stale indexes, partial publication, search relevance, graph inference, rights, phase/subject vocabulary and versioned generated artifacts.
- **Known failures or duplication:** the same identities and relationships can be represented in API data, application route models, search documents and graph structures; freshness and authority across them are not yet one explicit contract. Ground-truth references can outlive source slugs.
- **Historical reason or constraint:** API, SDK, search and graph capabilities were developed for different consumers and retrieval needs. Their existence and package boundaries do not prove either that they should merge or that they are genuinely separate authorities.
- **New chain evidence:** Database-Tools migrations, schema documents and materialized views encode curriculum state, lifecycle and public read projections; Hasura metadata exposes selected relations; oak-openapi pins independently versioned resolver names and adds transformation, rights and delivery policy; OCE retains a reviewed contract cache, generates transport surfaces and adds authored capabilities. No inspected boundary identifies one curriculum release, one placement set or one authority for every claim in that chain.
- **Correspondence evidence:** a local lockfile-checked, network-guarded comparison found the pinned oak-openapi document and OCE cache structurally equal after declared projection, with one retained prose difference. That is evidence of snapshot correspondence only; runtime payload, policy, publication completeness and future compatibility remain unproved.
- **Clock and outcome evidence:** authoring commit, materialized-view refresh, HTTP contract, OCE cache, bulk receipt, search/index state and consumer observation can advance independently. Accepted mutation, committed effect, projected state and public visibility are not currently one identified outcome.

Primary local evidence: [system map](../../current-state/system-map.md), [repository anatomy](../../current-state/repository-anatomy.md), [freshness and failure](../../current-state/freshness-and-failure.md), [teacher discovery to download](../../current-state/journeys/teacher-discovery-to-download.md), [pupil lesson to results](../../current-state/journeys/pupil-lesson-to-results.md), the [database/API/OCE repository atlas](../../current-state/database-tools/repository-and-contract-atlas.md), [authority and projection analysis](../../current-state/database-tools/database-authority-and-projections.md), [OCE consumer analysis](../../current-state/database-tools/oce-consumer-and-generation.md), [multi-lens synthesis](../../current-state/database-tools/concept-lenses/synthesis.md), and the [ecosystem enablement model](../../synthesis/ecosystem-enablement.md).

## Complexity classification

- **Essential domain complexity:** curriculum identity, sequence, variants, pedagogical relationships, content status, provenance, curation and what makes a result relevant for an audience and purpose.
- **Trust or policy obligation:** curriculum/content integrity, rights and licence, withdrawal, accessibility of discovery, query privacy, safe content and auditable publication.
- **Chosen system complexity:** OpenAPI and SDK shape, route taxonomies, Elasticsearch document/index models, graph protocols/stores, ingestion applications and cache topology.
- **Accidental or migration complexity:** legacy slugs and routes, duplicated application query models, cached schema hand-offs and obsolete ground-truth references, pending historical evidence.
- **Compensating mechanism:** identity mapping, aliases, reconciliation, repeated validation and special route logic may compensate for multiple representations without explicit shared provenance.
- **Unknown:** actual source of every fact, editorial authority for browse/search/graph, permitted freshness divergence, future consumer query needs, graph inference semantics and whether one model can remain conceptually coherent.

## Challenge the system

- Could one published, versioned curriculum representation directly support exact retrieval and browse without application-specific shadow models?
- Could database-native text/vector search meet discovery outcomes without a separately owned search SDK or ingestion domain?
- Could graph traversal be generated or evaluated at build/request time from explicit relationships rather than maintained as another store?
- Could curated discovery journeys reduce the need for open-ended search in some products?
- Could a publication event or immutable release artifact drive every projection with one acknowledged version?
- Could aliases and retired identities be governed once rather than repaired in each consumer?
- Are search relevance and graph inference genuinely curriculum facts, product decisions, learned evidence or technical index structures?
- Is the upstream API a necessary network boundary, or could products consume a versioned artifact or colocated authority?
- Does combining systems create an incoherent universal model, and would explicit federation be more honest?

## Excellence contract

- **Correctness and semantic integrity:** every field has a named authority and provenance; identity, sequence, variants and withdrawal are consistent or deliberately channelled; no projection silently invents source facts.
- **Curriculum and content integrity:** curriculum experts can validate meaning and pedagogy; source version, transformations and omissions are auditable; relevant educational context survives indexing and graph conversion.
- **Educational effectiveness:** discovery quality is evaluated against real teacher/pupil goals, not only exact slug position or technical retrieval metrics; relevance explanations distinguish source fact, curation and inference.
- **Accessibility and inclusive interaction:** discovery structures support understandable labels, keyboard/screen-reader use and alternatives to visually dense search/graph interfaces; output content retains accessible structure.
- **Safeguarding, privacy, consent, rights and security:** search queries and behavioural signals have explicit purpose/retention; content access and rights propagate; untrusted indexed content cannot create unsafe output or query behaviour.
- **Identity, state and effect semantics:** publication acceptance, projection start/completion, promotion and consumer visibility are distinct states; one version identifier follows data through every representation.
- **Failure acknowledgement and recovery:** stale, missing, partial or rebuilding projections are observable; consumers know whether to fail, degrade or use a named prior version; withdrawal has a bounded, proved path.
- **Reliability and operability:** projections rebuild and rollback; drift is detectable; checks distinguish source outage, transformation defect, index issue and consumer-cache issue.
- **Evolvability and conceptual coherence:** source concepts are not polluted by storage/index concerns; extensions name ownership and compatibility; consumers do not reverse-engineer identity rules.
- **Idiomatic language, platform, protocol and framework use:** structured parsers, schemas, database/search/graph capabilities and generated clients are used according to their strengths; custom protocols require a curriculum reason.
- **Developer, API and documentation experience:** SDK/query surfaces explain identity, version, freshness, provenance, errors and stability; fixtures and examples are generated from the same authority; diagnostics expose the failing stage.
- **Determinism, reproducibility and testability:** given a source release and versioned configuration, every claimed projection is byte- or semantically reproducible; nondeterministic ranking/inference is explicitly bounded and evaluable.
- **Automated and human evidence required:** schema/identity properties, projection rebuild comparison, withdrawal/freshness fault injection, relevance and graph expert evaluation, user discovery studies, rights/security review and operational recovery rehearsal.

## Conclusion

- **Outcome and obligations retained:** trustworthy curriculum identity, pedagogical context, discovery relevance, publication/withdrawal integrity and explainable provenance for every consumer.
- **Premises accepted:** none yet; the common vocabulary and repeated representations warrant investigation but do not prove one authority.
- **Premises rejected:** none yet.
- **Essential complexity:** curriculum semantics, version/publication governance, relevance and any genuinely curated or inferred knowledge.
- **Mechanisms removed or combined:** no decision earned. SDK, browse, search, graph and publication boundaries remain candidates for preservation, generation, federation, combination or removal.
- **Selected system shape:** unresolved among deterministic projections, immutable releases, event/materialized views, federated authorities, one read store, source-native queries or redesigned discovery.
- **Remaining unknowns:** deployed database/API correspondence, field-level provenance, curriculum and rights authority, release completeness, editorial ownership, projection reproducibility, permitted freshness divergence, query privacy and future consumer needs.
- **Evidence that would reopen the decision:** new curriculum concept or publisher, accepted search/graph fact not represented in the model, material relevance evidence, withdrawal incident, source-protocol change or a projection that cannot be reproduced.

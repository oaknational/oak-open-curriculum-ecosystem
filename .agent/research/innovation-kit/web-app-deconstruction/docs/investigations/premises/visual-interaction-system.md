# Visual and interaction system

## Decision boundary

This record asks which visual and interaction outcomes require an authoritative shared implementation and what form that authority should take. It does not begin from the premise that a React component library, CSS-in-JS runtime, primitive API, token package or product-local UI is required.

The Oak Innovation Kit is intentionally a framework for additional consumers. That makes the quality and usability of its UI capabilities an explicit concern; it does not determine their technical representation.

## Current observation

- **Literal behaviour:** Oak Components exposes tokens, styling utilities, layout and typography primitives, controls, composed patterns and OWA-specific recipes through one public package root. OWA adds local layouts, adapters and product components.
- **Inputs and outputs:** design decisions, content, interaction state and product context enter component props and theme/runtime context; output is styled React UI, semantic markup, browser interaction and event callbacks.
- **State and authority:** design values live in package source; theme and styled-components provide runtime style context; native browser state, React state and consumer-owned domain state meet inside controls and recipes.
- **Dependencies and lifecycle:** React, Next.js-related imports, styled-components, browser APIs and package exports can enter a consumer graph even for apparently foundational imports. Some composed recipes depend on private internal components.
- **Excellence currently delivered:** a recognisable Oak language, reusable layout and typography, accessible interaction patterns, consistent content presentation, strong TypeScript APIs, visual examples and product-specific recipes.
- **Difficult states and exceptions:** keyboard and focus behaviour, validation and errors, disabled/read-only state, responsive layout, reduced motion, long or translated content, server rendering, hydration, high contrast, media alternatives and asynchronous interaction.
- **Known failures or duplication:** one root export obscures conceptual and runtime layers; primitive imports can retain a broad dependency floor; OWA and the library can both own related recipes; public and private recipe boundaries do not always align with source dependencies.
- **Historical reason or constraint:** the package has accumulated from a component-library role and a single OWA hand-off. That history does not establish the best framework surface for additional OCE consumers.

Primary local evidence: [component boundary](../../current-state/component-boundary.md), [Oak Components runtime experiment](../../experiments/oak-components-runtime.md), [accessibility and assurance](../../current-state/accessibility-and-assurance.md), and [runtime-shell parity](../../current-state/runtime-shell-parity.md).

## Complexity classification

- **Essential domain complexity:** educational content hierarchy, audience-appropriate interaction, Oak product concepts, allowed states and the relationship between interaction and curriculum meaning.
- **Trust or policy obligation:** accessibility, readable content, reduced motion, focus and announcements, privacy in interactive telemetry, truthful disabled/loading/error states and rights-compliant media.
- **Chosen system complexity:** React prop APIs, styled-components, runtime theme providers, polymorphic layout primitives, recipe composition and a single package export surface.
- **Accidental or migration complexity:** legacy/current theme overlap in OWA, OWA-specific recipes in the library, private-internal recipe dependencies and root compatibility, subject to history.
- **Compensating mechanism:** broad primitives and variants may compensate for CSS or product composition that lacks an authoritative generated foundation; local adapters may compensate for product semantics missing from generic APIs.
- **Unknown:** authoritative design source, future host/framework range, exact supported browsers and assistive technologies, which recipes carry stable Oak meaning, and whether visual variation is theme, product or capability variation.

## Challenge the system

- Could design decisions be structured once and generate CSS, TypeScript, documentation, fixtures and non-web representations?
- Could semantic HTML plus CSS express layout and typography without a React primitive layer?
- Could platform controls or a proven headless behaviour library own difficult interaction while Oak owns appearance and content?
- Could an Oak-specific pattern belong to its capability instead of a global UI namespace?
- Could better content and journey design remove a complex widget entirely?
- Could validation and error semantics be part of typed forms or use cases rather than visual component props?
- Could CSS layers, custom properties, container queries and modern selectors remove runtime theme or responsive helpers?
- Does a component exist because it protects an outcome, because it is convenient, or because the current styling system makes ordinary markup difficult?

## Excellence contract

- **Correctness and semantic integrity:** visual state matches actual domain state; component names and props use product or platform meaning rather than styling accidents; one authority defines each token and behaviour.
- **Curriculum and content integrity:** patterns preserve curriculum hierarchy, attribution, licence and content meaning; truncation, responsive layout or interaction never silently hides necessary educational context.
- **Accessibility and inclusive interaction:** semantic HTML first; complete keyboard, focus, announcement, zoom/reflow, contrast, motion and target-size behaviour; representative assistive-technology evidence; no inaccessible fallback hidden by a passing static rule.
- **Safeguarding, privacy, consent, rights and security:** components do not collect telemetry by mounting; unsafe content and external media boundaries are explicit; private state is not encoded in visual utilities or URLs inadvertently.
- **Identity, state and effect semantics:** controlled/uncontrolled and server/client state contracts are explicit; visual components do not become hidden domain authorities; effects are surfaced to the owning capability.
- **Failure acknowledgement and recovery:** loading, empty, partial, stale, validation and terminal failure states remain truthful, readable and operable; focus and announcements follow recovery.
- **Reliability and operability:** server rendering and hydration are deterministic where promised; visual-regression evidence is complemented by semantic/interaction evidence; diagnostics identify the owning pattern and state.
- **Evolvability and conceptual coherence:** consumers can choose the narrowest meaningful surface; generated outputs trace to their source; variants represent real semantic differences; private dependencies do not leak into public guarantees.
- **Idiomatic language, platform, protocol and framework use:** HTML/CSS/browser capability is used directly where sufficient; React composition follows server/client semantics; custom widgets implement established accessibility patterns.
- **Product, service and interaction design:** patterns are derived from user purpose and context, not component inventory; content design and information architecture are reviewed with the interaction.
- **Developer, API and documentation experience:** every public surface states purpose, semantics, accessible contract, dependencies, supported hosts, examples, adverse states and testing guidance; invalid combinations are unrepresentable or diagnosed clearly.
- **Determinism, reproducibility, testability and diagnostics:** generated outputs are reproducible; interaction machines can be tested independently; fixtures cover content extremes; failures identify source decision, component/behaviour and consumer usage.
- **Automated and human evidence required:** source-to-artifact checks, type and module-boundary tests, SSR/RSC builds, browser and assistive-technology testing, content/design review, visual regression and representative consumer studies.

## Conclusion

- **Outcome and obligations retained:** coherent Oak expression, excellent educational content presentation and inclusive, reliable interaction for every intended consumer.
- **Premises accepted:** none yet; current evidence proves valuable shared knowledge and a broad coupled package, not its correct replacement shape.
- **Premises rejected:** none yet.
- **Essential complexity:** human interaction, content hierarchy, accessible state semantics and authoritative design decisions.
- **Mechanisms removed or combined:** no decision earned. React primitives, runtime theme, root exports, recipes and local adapters remain challengeable.
- **Selected system shape:** unresolved among preserved components, layered exports, generated/native foundations, narrow behaviours, capability-owned patterns and redesigned interactions.
- **Remaining unknowns:** future consumer/host needs, design-source authority, support matrix, recipe semantics and which variation is legitimate.
- **Evidence that would reopen the decision:** new accessibility or user evidence, browser-platform improvement, host change, product-pattern divergence, a broken assurance claim or proof that the chosen surface imports hidden runtime obligations.

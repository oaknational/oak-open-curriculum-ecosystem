# Investigation backlog

This backlog prioritises evidence that can invalidate or narrow the current hypotheses and guide the Oak Innovation Kit toward uncompromising product, design and engineering excellence. Priority reflects expected information value, not an OWA implementation roadmap.

OWA and Oak Components investigations serve the [ecosystem enablement model](../synthesis/ecosystem-enablement.md). They establish what Oak needs to make possible and why, including excellent current behaviour and difficult cases. Runtime probes are valuable when they clarify an outcome, premise, obligation, failure contract or compensating mechanism; they are not precursors to fixing the source systems.

The [capability coverage ledger](./capability-coverage.md) records mapped, partial and uninvestigated areas so this backlog cannot be read as evidence that the current journey set is complete.

## Investigation record template

Each new investigation should record:

1. question and decision affected;
2. scope and pinned sources;
3. observations;
4. purpose chain and explicit premises;
5. essential, chosen, accidental, compensating and unknown complexity;
6. system-changing and system-collapsing alternatives;
7. interpretations and competing explanations;
8. effect on each relevant hypothesis;
9. next discriminating evidence;
10. dated conclusion, including inconclusive results.

## Candidate executable experiments

Executable work follows an accepted [premise record](./premise-record-template.md). The next experiments should discriminate between whole-system alternatives rather than demonstrate a preferred architecture in isolation.

- A teacher-resource premise study comparing current download, direct delivery, generated artifact and redesigned-resource models.
- A pupil-session study comparing current routes/stores/projections with one authoritative learning-session model and any genuinely distributed alternatives.
- A visual-and-interaction study comparing Oak Components, generated tokens and CSS, native elements, shared accessible behaviours and framework components.
- An application-host study comparing shell profiles with direct request, route and isolated client-interaction composition.
- A curriculum-authority study testing whether API, browse, search, graph and publication require separate models or can be derived coherently from one authority.
- A saved-content study challenging whether each outcome requires accounts, durable state and optimistic client/server reconciliation.

The immediate, bounded reproductions are maintained in the [validation register](./validation-register.md).

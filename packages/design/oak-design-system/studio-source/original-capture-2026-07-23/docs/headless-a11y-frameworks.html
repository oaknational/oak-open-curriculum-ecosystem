Headless, accessibility-first component frameworks

Which behaviour-only ("headless") component libraries are fit to carry this design system's WCAG 2.2 AA-floor obligations when consuming apps need interaction logic we don't ship — comboboxes, dialogs, menus, date pickers.

Researched 19 July 2026 · rev 3 — direction refined: Base UI default · React Aria scoped non-default · Ark UI third · Ink for console TUIs · operative docs: consuming-nextjs.md §5b + the three pairing guides

Takeaways

  1. The headless model matches our contract exactly. These libraries own behaviour — keyboard navigation, focus management, ARIA semantics, RTL, controlled/uncontrolled state — and leave 100% of appearance to the consumer, which is where our role tokens, focus ring, and state rules live. Pre-styled libraries (MUI, Ant, Chakra) remain the wrong fit for re-brandable Oak UI.
  2. Owner direction (refined): Base UI is our default; React Aria scoped, not excluded. Base UI — built by the Radix, Floating UI and Material UI creators, backed by MUI's dedicated team — reached stable v1.0 (Dec 2025) with 35 components and is the actively maintained primitive layer (v1.3 as of mid-2026); Radix itself slowed after the WorkOS acquisition. React Aria (initially excluded by preference) is admitted as a documented non-default scoped to date/time + locale widgets and conformance-critical surfaces; Ark UI/Zag.js is the documented third for non-React surfaces. One pairing guide per library in docs/.
  3. React Aria (Adobe) remains the deepest accessibility implementation — 40+ WAI-ARIA patterns tested across ~30 screen-reader/browser combinations plus i18n depth — and the only credible accessible DatePicker story, which is exactly the scope it keeps here; its hooks-first model is the most code per component, against our avoid-complexity bias, so it never duplicates a widget class Base UI covers.
  4. "WAI-ARIA compliant" is a claim, not a guarantee. A Publicis Sapient screen-reader audit of Radix logged 35 issues (P1–P3), many still open in 2025. Whatever the consuming app adopts, our per-pairing audit and the a11y charter's "every build must still" list stay in force — the library removes a class of failure, not the obligation.
  5. For non-React or multi-framework consumers, Zag.js (vanilla-JS state machines, WAI-ARIA-modelled, Playwright-tested per spec) and its wrapper Ark UI (React/Vue/Solid/Svelte) are the credible options — same machines everywhere, styled via data-part/data-state hooks that take our tokens cleanly.
  6. Console TUIs are a separate stack: Ink. The ecosystem repo already ships a React console TUI (the collaboration TUI, agent-tools/src/collaboration-state/tui/, Ink v7 + ink-testing-library). None of the web headless libraries apply in a terminal — Ink's Box/Text primitives are the layer there, and the repo deliberately keeps it on “local Ink primitives” with no design-workspace dependency. What carries over is our vocabulary, not our CSS — see §TUI below.

What this means for Oak consumers

Default — Base UI

Owner direction plus the maintenance evidence line up: Base UI has the least API ceremony of the primitive layer (composition-style, learned from Radix's mistakes), a funded team committed to long-term maintenance, and v1.x point releases already shipping a11y fixes (e.g. iOS VoiceOver). Already in production at Paper, Zed and Unsplash. Radix remains acceptable in existing codebases but is no longer the default for new builds. Guide: docs/pairing-base-ui.md.

Scoped non-default — React Aria Components

Adobe's library is the sector's deepest screen-reader-tested implementation and the usual “conformance is contractual” pick. Direction initially excluded it outright; when the docs went multi-library it was admitted with scope: date/time + locale-aware widgets (its genuine monopoly) and conformance-critical surfaces — never duplicating a widget class Base UI covers. Guide: docs/pairing-react-aria.md.

Non-React and multi-framework — Ark UI / Zag.js

The documented third (chosen over Ariakit, which overlaps ~90% with Base UI's territory): the same WAI-ARIA state machines across React, Vue, Solid, Svelte and vanilla JS/web components; styling lands on [data-scope]/[data-part] attributes, so tier-3 tokens apply without adapters. Guide: docs/pairing-ark-ui.md.

Console TUIs — Ink

The ecosystem repo requires React-based console TUIs: the collaboration TUI (agent-tools/src/collaboration-state/tui/) is an Ink v7 app — React components rendering to the terminal via flexbox-like <Box>/<Text> — tested with ink-testing-library, with a documented boundary: it uses local Ink primitives and takes no dependency on a built design workspace. It already encodes a mini token system by hand: a StatusTone union (active/success/warning/danger/muted → cyan/green/yellow/red/dim) plus StatusBadge, Panel, OakText, and key-hint components.

What our system can and can't give a terminal:

  • Tokens port as a vocabulary, not as CSS. Terminal cells have no custom properties; the honest mapping is role-name → ANSI 16-colour, mirroring what the TUI's StatusTone already does (success/warning/danger/active/muted ≡ our text-success/error/warning/link/subdued roles). If more console surfaces appear, a tiny shared tones.ts (role names + ANSI mapping + the state-never-colour-alone rule) is the right artefact — not an Ink dependency from this project.
  • The a11y obligations translate. State never colour alone → the TUI's badges already pair colour with bracketed text labels; keep that. Honour NO_COLOR/dumb terminals → the tone map must degrade to plain text. Screen-reader access in terminals is line-based → the non-interactive --format text path (which the TUI ships) IS the accessible output; keep it first-class, never chrome-only.
  • 16-colour honesty: ANSI palette colours are themed by the user's terminal, so contrast is ultimately theirs — never encode meaning in colour pairs we can't guarantee (another reason the bracketed-label rule is load-bearing).
  • Web headless libraries have no role here. Ink is the framework and the primitive layer in one; the avoid-complexity call is to keep it exactly as the repo has it.

Non-negotiable regardless of library: adopting an "accessible" library discharges none of our obligations. The Radix audit episode is the proof case — externally logged screen-reader defects (P1–P3) persisted for years in the most popular primitive library. Concretely, for every wrapped component:

  • Re-apply the double focus ring on :focus-visible (headless libraries ship no focus styling at all — an unstyled primitive is invisibly focusable by default).
  • State never colour alone; targets ≥44px; probe every rendered pairing ×4 themes via preview/contrast-audit.html.
  • Honour data-motion — library-internal transitions must collapse under reduced motion.
  • Screen-reader spot-checks stay in the definition of done (per the a11y charter's "every build must still" column); axe-level automation misses the interaction subtleties these libraries exist to solve.

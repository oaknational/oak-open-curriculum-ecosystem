# OCE integrity and Castr integration

**Status:** programme architecture and derived implementation specification, 10 October 2026. Owner direction is identified separately from proposed mechanisms and unresolved bindings. This document establishes no implemented compiler, published package, live data service or qualified AI host.

**Editing authority:** Engraph owns this implementation specification and its delivery plans. Specialist source research retains its own authority; material changes to that research reopen affected requirements here. The complete contract required by an implementer is stated below, so implementation does not depend on access to private briefings or research storage.

## Purpose and scope

OCE must preserve required data meaning, identity, types, provenance and authority through acquisition, transformation, storage, generated interfaces, published packages and consuming instances. Keeping mechanisms together makes coherent construction and review possible; it does not itself prove any guarantee. Castr integration is settled owner direction. Its contribution is contract compilation, with the exact supported profile and replacement boundary qualified before reliance.

The programme retains independent responsibility for curriculum semantics, source admission, storage integrity, runtime effects, publication eligibility, current permissions, serving operation and actual consumer interpretation. A compiler cannot supply missing source meaning, confer authority or make a host preserve context. Every boundary below belongs to OCE's reusable mechanisms; an external app selects a supported configuration and published package closure.

The exploratory pedagogy project has two architectural approaches, possibly alternatives, possibly complementary: one uses an institutional host's AI runtime, and in the other the project's own organisation owns runtime and orchestration. Neither approach establishes fidelity. The curriculum infrastructure consumer and the exploratory pedagogy project are not aliases, and programme reuse does not expand either commission. Public curriculum access need not acquire learner identity, transcripts or persistent learner hypotheses. Personal information, teacher plans and learner evidence require separately justified purpose, authority, retention and disclosure; common code grants no shared credentials.

The shared privacy direction has four obligations: C-PRIV-01 requires necessity before collection; C-PRIV-02 minimises context, prompts, telemetry, caches, derived records, exports and backups as well as storage; C-PRIV-03 bounds delegated knowledge and action by purpose, scope and time; C-PRIV-04 compares useful provision and necessary safeguarding under progressively less identifying information, exposure and persistence. Anonymous/session-only operation, institution-held state and selective disclosure are candidates to examine. These are design obligations, not claims of demonstrated educational or legal assurance, and do not expand the curriculum infrastructure consumer's current scope.

## Preservation contract

The following requirements carry the identifiers established in the exploratory pedagogy project's source editions. They apply in full to paths bound to that project and inform reusable OCE capabilities without claiming that every OCE application has adopted the same profile.

| Requirement                         | Necessary engineering consequence                                                                                                                                                                                                                   |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C-DATA-01 Continuous typing         | Values remain bound to explicit domain types and meanings, including intermediate values. Static TypeScript declarations alone do not establish runtime continuity.                                                                                 |
| C-DATA-02 Complete definitions      | Complete structures, alternatives, constraints, cardinalities and ontological interpretation remain available under exact versioned bindings. An unsupported target must retain an enforced obligation or reject the affected target.               |
| C-DATA-03 First-class relationships | Domain relationships have identity, type, participants/roles, meaning and lifecycle. Retain consequential direction, order, multiplicity, qualifications and provenance; distinguish relationship identity from independent assertion acts.         |
| C-DATA-04 Fidelity                  | Representation changes preserve the defined information continuously. Keeping a richer record elsewhere does not permit intermediate erasure followed by reconstruction.                                                                            |
| C-DATA-05 Selection and derivation  | Select fewer complete entities or explicit references within a declared scope. A summary, inference, embedding or aggregate is a separately typed derived artifact with input provenance; it cannot impersonate the source entity.                  |
| C-DATA-06 Epistemic states          | Observation, declaration, hypothesis, decision and enacted action remain distinct. Unknown, absent, empty, withheld, not applicable and partial have domain-defined meanings.                                                                       |
| C-DATA-07 Identity and evolution    | Preserve complete source keys and established IRIs. Entity, occurrence, relation, assertion, revision and serving generation have distinct lifecycles. Corrections change explicit revisions.                                                       |
| C-DATA-08 Actual context            | Required data and definitions reach the actual agent context intact for the claimed lifecycle. Agent output is a typed candidate; structure, meaning and authority must be checked before admission. No model-internal reasoning guarantee follows. |

Complete bindings may share definitions within one exact, available, immutable closure; definitions need not be repeated per scalar. A mutable URL, optional documentation lookup or post hoc source retrieval is insufficient. A typed natural-language utterance need not pretend all its meaning has been formalised; an interpretation of it is a separate claim.

Preservation and privacy interact through honest selection. Complete meaning does not require collecting everything or disclosing protected facts. If required interpretation would reveal unauthorised information, return a permitted typed reference/outcome or decline the affected operation. Do not leak a protected record's existence through an overly detailed absence reason. A refusal-only service also fails a positive capability it promises; a smaller supported scope must still complete its promised task.

## Identity, observation and compatibility

Identity is a domain promise rather than a database type. Preserve these distinctions in contracts:

- An enduring entity can have several revisions and occur more than once in a sequence.
- A relation and two independent assertions of that relation can have different withdrawal and evidence lifecycles.
- A source row key is source-qualified and complete; editorial state is not automatically a revision. Several source aliases can denote one entity.
- A serving generation identifies an admitted observation, not new curriculum identity. A rebuild must recover allocated identities.
- A content digest, representation ETag, logical specification UUID, release version and policy version are not substitutes for one another.

The exploratory pedagogy project's new owned identities use UUIDv7 and the agreed stable HTTPS direction; allocator, namespace stewardship, spelling and resolver behaviour remain exact design bindings. Preserve established upstream IRIs. Equal UUID suffixes in distinct IRIs do not establish equivalence. UUID allocation does not prove uniqueness of the represented domain thing.

Every meaningful result identifies its contract/projection, selected generation, source basis, exact required definitions, coverage, source freshness and applicable current eligibility. A snapshot can contain an explicitly compatible set of independently published revisions; a local generation does not falsely attribute a coordinated release to publishers.

Coherent enumeration binds a cursor to generation, query, projection and stable total order. A cursor grants no authority. On truncation retry from the last accepted envelope; on expiry restart under a new observation rather than mixing generations. Ranked top-k search is not an exhaustive census. Search operating details remain in the separate search work.

Compatibility includes semantic and behavioural changes: defaults, ordering, enum handling, references, completeness, retention, permitted effects and error/recovery rules, as well as field shape. Define supported version combinations and consumer upgrade/rollback paths. Retire an old export only when every known consumer is migrated or deliberately retired with evidence. Permanent coexistence or hidden fallback is not the default migration strategy.

Castr can reduce separately maintained interpretations of application contracts and provide explicit diagnostics and consistent generated representations. It does **not** guarantee curriculum truth, complete source capture, relational transactions/foreign keys, identity allocation, rights, permissions, migration, graph-native semantics, search relevance, correct runtime effects, intact host context or educational benefit. Shared generated artifacts can share one defect; independent source-semantic and domain-semantic fixtures remain essential.

### Profile mismatches that must be resolved before replacement

1. **Unknown-key policy:** draft SPEC-P-1 reads an unstated object policy as closed and reports that choice. This can differ from the source dialect's native reading. Call it a declared Castr profile, not unconditional source fidelity. Bind the raw source, any separately authorised corrected/profiled contract and the consumer promise explicitly.
2. **Defaults:** the draft's ratification checklist identifies a change from current OCE `.default()` output: a JSON Schema/OpenAPI default is treated as annotation rather than value insertion. Decide the intended parsed-value contract and fixtures; do not preserve an accidental old generator behaviour as the oracle.
3. **Target editions:** the exploratory pedagogy project's inherited API design selects OpenAPI 3.2.1; draft Castr's writer table selects 3.2.0. The exact supported canonical/writer/validator combination must be reconciled through the respective authorities. No silent downgrade or assertion that patch versions are equivalent.
4. **Boundary meaning:** actual method, operation identity, parameter location/serialization, response exact/range/default status, media and header semantics need independent source-derived checks. A compiling `paths` type can still be unusable if its status keys disagree with the consuming client.
5. **Extractability and CF:** draft Castr Home says no Castr workspace depends on an OCE package outside Castr; this condition is listed for ratification. OCE source custody is compatible with an isolated workspace group. Automatically importing shared CF packages into that group would violate the proposed boundary. Resolve whether self-contained Castr primitives, a clarified permitted shared-foundation boundary, or another explicit structure meets both requirements. Do not copy a common implementation into two authorities or treat the entire Castr source as a required CF prerequisite.

The integration location is settled by the owner commission. Exact seams, profile choices, model shape, migration technique and ratification state remain bounded decisions. Their absence blocks the dependent replacement, not the broader OCE architecture.

## Qualification and unresolved bindings

The [OCE architecture](oce-architecture.md) owns the surrounding responsibilities and dependency rules; [configuration contracts](oce-configuration-contracts.md) owns ordinary instance variation and its enforcement. These permanent obligations outlive any delivery tranche.

Before relying on a supported boundary, bind the selected source/profile/target definitions, allocation and namespace rules, finite freshness/retention/withdrawal policy, compatibility range and the responsible authority. Before replacing a compiler path, resolve Castr ratification, model disposition, extractability/CF dependency boundaries and every consumed output. Before claiming host-context preservation, obtain exact host and lifecycle evidence. Before processing protected educational context, establish purpose, delegated authority, retention, correction and receiving obligations.

An unresolved binding blocks only the operation or guarantee that depends on it. It does not automatically block all OCE development, public curriculum design or an independently complete foundation. Implementation sequencing and changing delivery status belong in the programme records, not in this architecture's authority.

A bounded integrity qualification begins with one independently expected contract fixture, without first requiring the full curriculum model. Its output must include the entity/revision/occurrence/assertion definitions, source mapping, generation and eligibility rules, complete input/output variants, target enforcement allocation and a reproducible source-to-wire trace. The first fixture contains no personal data or restricted material.

The following are software acceptance obligations for a supported boundary, not evidence of tests already run:

| Case                                                     | Required observation                                                                                                                                   |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Same lesson twice; two assertions of one relation        | Occurrence order/multiplicity and independent assertion provenance survive all representations.                                                        |
| Missing identity, qualifier or definition                | Explicit admission/target failure; no later lookup disguises intermediate loss.                                                                        |
| Unsatisfiable source schema or an unstated object policy | Faithful diagnosis/profile disclosure; no guessed repair or silent contract change.                                                                    |
| Source refresh during request/pagination                 | One promised observation or explicit expiry/restart; no mixed complete result.                                                                         |
| Wrong body under a valid transport status                | Actual status/media selects the branch; shape matching cannot relabel the response.                                                                    |
| Old data withdrawn before rollback                       | Current eligibility blocks future release, including asset/cache routes.                                                                               |
| Generator outputs agree but share a removed constraint   | Independent source-semantic negative fixture fails the candidate; self-round-trip success is insufficient.                                             |
| Packed consumer and supported configuration change       | Public imports, assets, runtime validation, diagnosis and release work without checkout internals or an OCE edit/new release for the supported change. |

## Wider innovation coverage

The matrix is not limited to today's MCP or search applications. OCE retains the construction and operating facilities needed for authoritative definition modules, source adapters, data pipelines, experiment fixtures, graph/query capabilities, reusable policy enforcement, contract generation, package distribution, host bindings, diagnostics, recovery, correction and future authoring/publication. Capability construction can proceed incrementally with exact consumers and evidence.

Future authoritative commands, asset/review/publication operations, protected purpose/work/evidence exchange, exact continuation, educator return/correction and supported provider exit have separate authority and operational contracts. They remain legitimate OCE capability homes. They are not implied implementations or prerequisites for the initial public curriculum slice. CF construction strengthens their foundations without forcing every useful seam to wait for all CF units.

The strongest counterframe is ordinary typed APIs with compact text and a richer source retained upstream. It can serve deliberately narrower applications, but it fails the exploratory pedagogy project's preservation profile where required meaning is erased in the used representation. The proportionate response is a smaller complete supported capability, or a different qualified target, rather than a weakened guarantee. Conversely, a universal IR or generic workflow engine is not needed merely to honour explicit contracts.

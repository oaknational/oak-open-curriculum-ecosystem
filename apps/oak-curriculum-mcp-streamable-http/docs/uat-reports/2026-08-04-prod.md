### F1 — `get-key-stages-subject-lessons` limit semantics (P1)

**Repro.** `get-key-stages-subject-lessons { keyStage: 'ks2', subject: 'maths', limit: 5 }`.
**Documented** (the tool's own schema): _"Limit the number of lessons returned per unit. Units
with zero lessons after limiting are omitted."_ **Observed:** exactly ONE unit
(`2-4-and-8-times-tables-…`) carrying 5 lessons; the other ~87 KS2 maths units absent.
**Why it matters:** a consumer paginating "5 lessons per unit" to walk the estate silently
receives one unit's worth and cannot tell the difference — the honest-window property the
graph tools hold is missing here. **Disposition:** fix the implementation to match the schema,
or re-word the schema and add the pagination signal; either way the two must agree.

### F2 — per-build widget resource URI (P2)

**Repro (observed, not constructed).** `resources/list` at 08:38Z advertised
`ui://widget/oak-curriculum-app-85820fb2.html`. After the 1.148.0 deploy, `resources/read` on
that URI returned "Resource not found"; a fresh `resources/list` advertised
`…-918e8e37.html`, which reads correctly (a complete 595 KB HTML document, Oak brand styles
and `<div id="root" data-mcp-app="oak-curriculum">` present).
**Why it matters:** the URI is content-hashed per build (deliberate — the served-surface
definition computes it), and the transport is stateless, so a client that cached the list
cannot be told the URI moved. Every deploy silently breaks the App surface for any host that
does not re-list. **Disposition:** either serve a stable alias URI alongside the hashed one,
or emit `notifications/resources/list_changed`, or document "re-list on a widget 404" as the
client contract. Worth a ticket; it is invisible until an Apps host is in use, which is
exactly when it will hurt.

## How this run was driven

The server ran locally in `observe-noauth` mode on port 3333 with the two
Elasticsearch keys injected from the search CLI's local env (the MCP app's own
`.env.local` carries only the API key and the auth switch, and env validation
refuses to boot without Elasticsearch). A scratch harness posted one
`tools/call` per probe over the Streamable HTTP endpoint and recorded, for
each: the JSON-RPC outcome, `isError`, `structuredContent.status`, the data
shape and length, the `pagination` echo, byte size and latency. Every
anomaly was then re-checked directly against
`https://open-api.thenational.academy/api/v0` with the same API key, so each
finding below is attributed to the server or to upstream on evidence, not
inference.

Probe families per tool (the "every shape" contract):

- every required-only call with real slugs harvested live from
  `get-subjects-programmes`, `get-threads`, `get-key-stages-subject-units`
  and `get-key-stages-subject-lessons`;
- every enum value where the enum is small enough to enumerate (17 subjects
  across the four subject-keyed tools, 4 key stages, 6 exam boards, 9 asset
  types on each assets tool, 12 year values on `get-sequences-units`, all 5
  search scopes, every `get-units-summary` factor);
- every optional parameter alone and in combination;
- pagination walks on the six paginated tools (first page, next page from
  the echo, page beyond the end, `limit` at its ceiling and one past it, zero,
  negative, fractional, string-typed);
- each aggregated tool's cross-field rules (anchor-mode exclusivity, thread
  window on a non-thread anchor, suggest without a context filter, threads
  scope without query);
- negative shapes: missing required, wrong type, uppercase enum, unknown
  enum, unknown slug, empty-string slug, unknown extra property,
  non-object `arguments`, unknown tool.

Rate-limit cost of the whole run: about 330 upstream calls of the 1000 window
(672 remaining at the end, reset 12:00Z).

## Findings in detail

### P1 — stale-spec silent truncation on two passthrough tools

Upstream 0.11.0 added `offset` and `limit` (default 20, max 300) with a
`Link: rel="next"` header to `/key-stages/{ks}/subject/{subject}/units` and
`.../assets`. The cached 0.7.0 spec has neither parameter on those two paths,
so the generated tools send no `limit`, receive the default first page of 20,
and — because the generator does not classify them as paginated — discard the
`Link` header and return without a `pagination` field. The result looks
complete and is not.

Measured (local tool result vs upstream with `limit=300`):

| Call                  | Local tool returns      | Upstream total              |
| --------------------- | ----------------------- | --------------------------- |
| `ks2` `maths` units   | 1 year group, 20 units  | 4 year groups, 88 units     |
| `ks4` `science` units | 1 year group (year-10)  | 2 year groups, 55 units     |
| `ks3` `english` units | 3 year groups, 20 units | 3 year groups, 25 units     |
| `ks2` `maths` assets  | 18 lesson groups        | more than 597 lesson groups |

The KS3 English row is the dangerous shape: the same number of year groups
comes back, so nothing in the payload hints that five units are missing. The
tool description still promises "a flat list of every unit with published
lessons in a key stage + subject".

Disposition: the MCP-630 spec-cache refresh regenerates both tools with
`limit`/`offset`; the generator's `isPaginatedQueryMetadata` then marks them
paginated, and the pagination echo landing on `feat/mcp-pagination-echo`
covers them with no further code. Until the refresh lands, the two tools
under-report on any key stage × subject with more than 20 units or 20 lesson
asset groups, which is most of them. Sequence this branch, then the refresh.

### P2 — search `size` above 80 fails on every RRF scope

`search` declares `size` in `[1, 100]` (`aggregated-search/flat-zod-schema.ts`).
The RRF retrievers set `rank_window_size: 80` (`oak-search-sdk`
`rrf-query-builders.ts`), and Elasticsearch rejects any request whose `size`
exceeds the window:

```text
action_request_validation_exception: Validation Failed: 1: [rrf] requires
[rank_window_size: 80] be greater than or equal to [size: 100]
```

Bracketed live: `size: 80` succeeds, `size: 81` fails, on `lessons`, `units`,
`threads` and `sequences`. `suggest` (lexical, no RRF) accepts 100. Cure: either
cap the schema at 80 or derive the window from the requested size; the schema
and the retriever must agree at the boundary.

### P2 — upstream 500s where 404s belong

Direct upstream evidence, same key:

```text
GET /lessons/no-such-lesson-xyz/transcript  -> 500 {"message":"Cannot read properties of undefined (reading 'replace')"}
GET /programmes/no-such-programme           -> 500 {"message":"Programme not found: no-such-programme","code":"INTERNAL_SERVER_ERROR"}
GET /programmes/no-such-programme/units     -> 404 {"message":"Programme not found","code":"NOT_FOUND"}
GET /lessons/no-such-lesson-xyz/summary     -> 404 {"message":"Lesson not found","code":"NOT_FOUND"}
```

The server classifies both correctly as `UPSTREAM_SERVER_ERROR` and the agent
sees "Upstream server error (500): …" with the upstream message. Nothing to fix
locally; route both as upstream bug reports per ADR-222.

### P3 — the classifier drops the upstream 400 `issues` detail

`get-keywords {}` reaches the agent as `Input validation failed`. Upstream's
400 body carries the actionable line in `issues[0].message`:
"At least one of subject, keyStage, phase, unit or lesson must be provided".
`classify-error-response.ts` `extractErrorMessage` reads the top-level
`message` only, so the loss applies to any upstream 400 whose actionable
detail lives only in `issues`. Cure: append the first `issues[].message`
when present.

### P3 — runbook drift on the validation-error shape

Runbook §12.2 and the response-shape contract say an input-schema violation
surfaces as a JSON-RPC `-32602` error. On this server every generated and
aggregated tool returns a **tool result** with `isError: true` and text
`MCP error -32602: Input validation error: Invalid arguments for tool …` (56
probes, consistent). The only JSON-RPC-level error observed was a non-object
`arguments` value (`"arguments": "ks2"`), rejected by the transport schema
with a Zod issue list. The behaviour is honest and consistent; the runbook
cells are stale.

### P3 — upstream quirks worth a bug report each

- `/lessons/{slug}/quiz` for an unknown slug returns `200 {"starterQuiz":[],"exitQuiz":[]}`
  where the sibling summary/assets/transcript paths return 404 (or 500 above),
  so an agent cannot tell a missing lesson from a lesson without quizzes.
- `/sequences/science-secondary` and `/sequences/english-secondary` return 404
  "Sequence not found" while `/sequences/<same>/units` returns 200 with five
  year groups (257KB for science). The sequence exists for one path and not
  the other.
- `limit: -1`, `offset: -5` and `limit: 2.5` on the paginated tools reach
  upstream (the spec declares plain `number`) and come back as 500s leaking
  GraphQL validation text. `limit: 0` returns `200 []`. Upstream should
  declare `integer`, `minimum: 0`; a local `param-description-overrides`
  floor would also cure it.
- `get-keywords` description says `phase` cannot be combined with `keyStage`;
  upstream accepts both and returns key-stage-scoped results.
- `get-units-summary` on a science unit with `tier: core` or any `pathway`
  returns a bare "Unit not found", while a `childSubject` mismatch returns a
  helpful factor-specific message.

### P3 — inconsistent strictness on argument objects

Generated tools with parameters use a strict object and reject
`{"foo": 1}`. The zero-argument tools (`get-key-stages`, `get-subjects`,
`get-threads`, …) expose `{}` and accept any property; `search` accepted
`foo` too. Harmless today, but the boundary rule is strict validation, and a
misspelt optional filter on `search` (say `keystage`) is silently ignored
rather than refused.

## Things that worked and are worth recording

- All 40 listed tools answer; 6/6 resources read (the widget at 608KB with the
  `mcp-app` profile); `prompts/list` is `-32601`; the two dormant resources
  and the dormant EEF tool are absent and refuse correctly.
- Pagination echo (this branch) is honest on all six paginated tools:
  `hasMore: true` with `nextOffset`/`nextLimit` on first and middle pages,
  `hasMore: false` on the last page, on a page beyond the end (`offset:
100000` → `[]`), on `limit: 0`, and on a narrowed call that fits in one
  page (`unit` filter on lessons). Non-paginated tools carry no `pagination`
  field.
- Every enum value on every enumerated parameter is accepted upstream: all 17
  subjects on the four subject-keyed tools, all 9 asset types on all four
  assets tools, all 12 year values, all 6 exam boards (eduqas/wjec/edexcelb
  return `[]` for KS4 science, which is true of the corpus).
- Graph tools behave to the working-with-graphs doctrine: unknown anchors are
  reported not errored (`unknownAnchors`), `depth` 0..3 grows the subgraph
  monotonically (1.9KB → 22KB), the thread window is honest (`hasMore`), and
  every cross-field refusal is typed.
- `download-asset` for a type the lesson lacks lists the available types in
  its refusal; for an unknown lesson it names the tools to find the slug.
- `get-sequences-units` accepts `year: 3` (integer) despite the string enum —
  lenient coercion, harmless.
- Large payloads (the known size class, not faults): `get-sequences-assets`
  without `year` 3.9MB (1065 items) and 661KB with a year; `browse-curriculum
{}` 569KB; `get-keyword-graph limit: 100` 537KB; `get-misconception-graph`
  thread window at `unitLimit: 25` 326KB; `get-keywords limit: 300` 269KB.
- Latency: everything upstream-backed answers under a second except
  `search scope: units` (7.3s and 3.9s on two queries) and `explore-topic`
  with a nonsense query (4.6s).
